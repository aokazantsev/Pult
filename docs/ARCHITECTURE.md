# Pult — архитектура и протокол

Pult — пульт для ИИ-агентов на ПК: телефон показывает, что делают треды агента (Claude Code, OpenCode
и другие), и позволяет ответить на запрос разрешения, вопрос с вариантами или продолжить тред текстом, не
подходя к компьютеру.

## 1. Границы

**Входит:**
- лента тредов на телефоне (сообщения агента и пользователя, вызовы инструментов, запросы) со статусом
  (работает, закончил, ошибка) и отметками «ждёт действия», «ждёт текста», «стоит в диалоге на ПК»;
- ответ с телефона на запрос разрешения и вопрос с вариантами (если адаптер умеет), ответ текстом в конце
  хода агента;
- самостоятельное развёртывание сервера-реле.

**Не входит (MVP):**
- захват экрана и имитация кликов;
- веб-панель и учётные записи;
- прерывание агента посреди хода, новый тред с телефона, ход рассуждений модели в ленте;
- iOS: только Android (D-7);
- пуши, системные уведомления, звук и вибрация: пользователь сам смотрит в приложение на экране (§7);
- публикация в RuStore — отложена на неопределённый срок (§11).

## 2. Компоненты

Монорепозиторий, лицензия MIT, четыре блока.

| Блок | Что делает | Кто разворачивает |
|---|---|---|
| `protocol` | спецификация, схемы сообщений, эталонные векторы криптографии | — |
| `desktop` | фоновое приложение в трее + хуки агентов, по образцу AgentGlow (D-54) | пользователь на своём ПК |
| `server` | реле на Python 3: соединения, маршрутизация, очередь недоставленного | мы на своём стенде (D-55) или пользователь где угодно |
| `mobile` | приложение Android на KMP + Compose Multiplatform, по образцу DevAtlas (D-53) | только мы, APK в GitHub Releases |

### Desktop

- **Фоновое приложение** держит ключи ПК, соединение с сервером и состояние тредов. Отвечает хукам
  по локальному каналу, недоступному другим учётным записям ПК, и только по локальному секрету установки.
  Хуки и секрет в настройки агента прописывает установщик (D-54).
- **Окно desktop** — переключатель режима «управление с телефона» / «управление с ПК» (§5.3), кнопка
  «Разорвать» и новый QR (§5.4). Режим меняется только здесь; сессия стартует в режиме «с телефона» и
  сохраняет его при восстановлении связи (§5.4).
- **Хуки** — небольшая программа рядом с фоновым приложением, которую агент вызывает как команду на свои события
  (D-54). Сама по сети не ходит: передаёт событие фоновому
  приложению и, если событие блокирующее, ждёт его ответа. До передачи события и секрета хук убеждается,
  что локальный адрес держит наше фоновое приложение. Агент этого не проверяет, поэтому его собственные
  HTTP-хуки не используются (у Claude Code они к тому же не поддерживают начало треда).
- **Адаптеры агентов** приводят события, транскрипт треда (фоновое приложение читает его по мере записи)
  и данные агента о тредах (название, папка начала, продолжение, форк, родитель) к общим типам протокола.
  Новый агент — новый адаптер, ядро не меняется. Формат транскрипта агент не обещает держать (F-10): запись,
  которую адаптер не понял, пропускается, лента получает пометку «часть записей не распознана», статусы и
  запросы идут от хуков и от этого не зависят (статус «ошибка» — событие агента об окончании хода с ошибкой,
  F-16). По транскрипту треда с открытым запросом или окном текста адаптер видит то, о чём хуки молчат: отказ
  в диалоге на ПК и ввод, вставший в очередь агента (§5.3). Перечень папок для экрана QR строит адаптер (D-59).
- Фоновое приложение не запущено или связь с ним оборвалась — хук сразу возвращает «нет решения», агент
  показывает свой обычный диалог. Pult никогда не блокирует агента дольше настроенного ожидания Pult: срок
  отсчитывается независимо от фонового приложения и меньше таймаута хука у агента, а решение принято, только
  когда хук подтвердил, что взял его (§5.3 п. 8). Таймаут хука у агента — запасной предел: по нему агент
  убивает процесс хука и считает это «нет решения», не отказом (F-6, D-40).

### Server

Тупое реле. Знает пары, открытые ключи и причины удаления пар (§5.4), пересылает зашифрованные конверты,
хранит недоставленные до истечения их срока. Это состояние лежит на диске и переживает перезапуск сервера
(D-55). Содержимое не видит и не может подделать. Исходящих запросов не делает.
Ограничивает число заявок и пар с одного адреса, срок хранения, размер конвертов и трафик.

### Mobile

Хранит одну сессию (сервер, пара, ключи ПК), держит поток, пока на экране (§7), показывает ленты тредов
карточками общего формата (§6.3). Треды сессии — списком в навбаре со статусом и отметками (§1). Название
присылает desktop: из данных агента, иначе первое сообщение и папка проекта. Вход — по биометрии или PIN,
повторно — при возврате на экран после блокировки или сворачивания дольше порога (D-51).

## 3. Ключи и доверие

- Алгоритм — **P-256**: ECDSA для подписи, ECDH для общего ключа. Причина — аппаратное хранилище Android
  Keystore (F-3).
- У каждой стороны две пары ключей: подпись и согласование. Закрытые не покидают устройство (телефон —
  Android Keystore, ПК — хранилище ОС), сервер хранит только открытые.
- Общий ключ пары — из согласования ключей ПК и телефона; из него выводятся ключи двух направлений. Ими
  шифруются и аутентифицируются все сообщения пары. Сервер их вычислить не может.
- Ключи ПК телефон берёт из QR, ключи телефона ПК проверяет по одноразовому секрету из QR, которого
  сервер не получает (§5.1). Сверка отпечатка — дополнительная защита.
- Форматы, выведение ключей, заверение, вход и подпись — `protocol/CRYPTO.md`.

## 4. Транспорт

- HTTPS до сервера у ПК и у телефона, одна схема для обоих: события от сервера — поток SSE, свои
  сообщения — HTTP-запросы `POST`. Подтверждение приёма — ответ на `POST`, подтверждение доставки —
  отдельный `POST` получателя (§6.2).
- Вход по принципу «вызов — ответ»: сервер присылает случайное значение, клиент подписывает его ключом
  подписи и открывает поток. Каждый `POST` подписан ключом подписи и привязан к открытому потоку;
  долгоживущих токенов нет. Исключение — запросы до появления пары (заявка ПК, ключи телефона, §5.1) и запрос вызова:
  их защищают одноразовая заявка, секрет QR, одноразовый вызов и ограничение частоты (§2, Server).
- Об открытии и закрытии потока телефона сервер шлёт ПК служебный сигнал, как «телефон несовместим»
  (§6.4); для ПК это «приложение на экране» (§7). Входящему ПК сервер сообщает текущее состояние, до
  этого ПК считает поток закрытым; окно текста, открытое до входа ПК в пределах порога живости (ниже),
  ждёт этого сигнала. Сигнал «закрыт» и текущее состояние идут после всех принятых от телефона сообщений.
- Поток без признаков жизни дольше порога сервер считает закрытым; замена потока в пределах порога сигнала
  не даёт. От того же признака у ПК считается «ПК без связи» (§5.4).
- Поток оборвался — клиент переподключается сам (телефон вне экрана — нет, §7); пропущенное за время
  обрыва приходит снимком (§5.2) и из очереди сервера (§6.2).
- `GET /info` сервера отдаёт поддерживаемые версии протокола; клиент проверяет их до сопряжения и при
  каждом подключении (§6.4).

## 5. Сценарии

### 5.1. Сопряжение

1. Пользователь ставит desktop и задаёт адрес сервера (по умолчанию — наш).
2. Desktop создаёт ключи, регистрирует на сервере одноразовую заявку и показывает QR: адрес сервера,
   идентификатор заявки, одноразовый секрет, открытые ключи ПК, версия протокола, срок простоя (§5.4).
   Серверу уходят заявка и открытые ключи ПК, секрет — никогда. До показа QR, как и срок, пользователь
   отмечает папки проектов, показанные с их последними тредами (по умолчанию 5 по активности, отмечено
   всё); вложенная папка — внутри отмеченной, отдельно не отмечается (D-59, §5.2).
3. Телефон сканирует QR, создаёт свои ключи, заверяет их секретом и отправляет на сервер вместе с
   идентификатором заявки.
4. Сервер передаёт ПК ключи телефона. Заявка сгорает; повторный скан показывает «QR уже использован,
   нужен новый на ПК».
5. ПК проверяет заверение. Сошлось — сессия за тем, кто отсканировал первым: пара активна, QR исчезает,
   ПК шлёт `hello`; без него телефон за срок ожидания удаляет пару (`protocol/CRYPTO.md`). Не сошлось — новая пара
   удаляется, ПК сообщает о попытке и предлагает новый QR. Отпечаток — для дополнительной сверки.

`hello` телефон шлёт при каждом подключении.

Строго один ПК и один телефон; несколько ПК или серверов на телефоне не поддерживаются. Успешное новое
сопряжение на любой стороне — обычный разрыв прежней сессии этой стороны (§5.4).

### 5.2. Статус и лента треда

Хук сообщает событие, адаптер — новые записи транскрипта → фоновое приложение обновляет статус и ленту
треда → отправляет на телефон, если он подключён. Пользователь видит их, пока приложение
на экране (§7).
На `hello` телефона и после своего подключения ПК шлёт снимок: треды со статусами, открытые запросы, исходы
последних закрытых запросов (D-82), отметку «стоит в диалоге на ПК» у тредов, чей запрос стоит в обычном диалоге,
и режим (D-49); за снимком — хвосты лент от того, что телефон уже видел (D-81, `protocol/MESSAGES.md` §6). Потоком эту отметку ставит запрос
разрешения или вопрос треда сессии (не окно текста), когда он стоит в обычном диалоге агента (D-34). В
desktop-приложении Claude Code диалог показан с первой секунды запроса, параллельно хуку (F-1), — отметка
ставится сразу, у запроса, ушедшего на телефон, рядом с «ждёт действия». Иначе — когда хук отдал запрос
диалогу: `resolved` «истёк» или «решено на ПК» при переключении режима и запрос, сразу ушедший в диалог (режим
«с ПК», несовместимые версии, вопрос, который адаптер не умеет передать), — без «ждёт действия». Отметку
снимает ответ в диалоге — событие, которое адаптер признаёт продолжением работы после диалога (у Claude Code —
`PostToolUse` того же инструмента после разрешения, записи отказа в транскрипте после отказа), а не
уведомление о показе диалога (F-18); снимает её и ответ телефона, взятый хуком: диалог desktop-приложения закрывается
вместе с хуком (F-20).
С карточек, которых нет в снимке, телефон снимает действия; незакрытый запрос, которого нет в снимке, показан «неизвестен»,
пока `resolved`, исход или тот же открытый запрос в следующем снимке не уточнит его; тред, которого нет в снимке, уходит
с телефона вместе с карточками (`protocol/MESSAGES.md` §4.6, §6.4). Снимок дополняет имеющуюся ленту; если
он с ней не стыкуется, на стыке — пометка «пропущены записи». Снимок и лента — только о тредах
сессии: тред появляется с первого своего события после сопряжения, история до сопряжения не передаётся.
Членство — по папке проекта (D-57): в сессию входит любой тред, начатый в отмеченной при QR папке или
вложенной в неё (D-59), по первому событию; папка начала не определилась однозначно — тред на ПК. Родство — только для показа:
продолжение — та же лента и тот же пункт списка, форк — пункт «форк …», не определилось — отдельный пункт.

**Дочерние треды** — запущенные другим тредом (оркестратор → дочерний). Родителя адаптер берёт из данных
агента (F-14). Если родитель в сессии, дочерний стоит под ним и его первое событие выводит в список и
родителя — пунктом без ленты до собственного события родителя; иначе дочерний — отдельный пункт. У
родителя видна сводная отметка «ждёт действия» или «ждёт текста», если такая есть хоть у одного дочернего. Сообщения между
тредами — записи ленты обоих тредов с пометкой, от какого треда. Запросы и окно текста дочернего треда — как
у любого (§5.3); вопрос не через хук на телефоне не виден (§9).

### 5.3. Запрос разрешения, вопрос с вариантами, ответ текстом

1. Агент вызывает блокирующий хук. Хук передаёт запрос фоновому приложению. В desktop-приложении Claude Code
   обычный диалог показан на ПК сразу, параллельно хуку (F-1): тред с первой секунды отмечен «стоит в диалоге
   на ПК» (§5.2), ответить можно и на ПК, и на телефоне. В CLI диалог появляется, когда хук вернул «нет
   решения». Где тред, адаптер видит по данным события (признак desktop-приложения — F-14).
2. **Маршрут.** Решает переключатель в окне desktop. Режим «управление с ПК», тред вне сессии (§5.2), нет
   активной сессии, сервер явно отказал в приёме, несовместимы версии по последнему `hello` (§6.4) — хук сразу возвращает «нет решения», агент показывает обычный диалог. Иначе запрос
   уходит на телефон; пока desktop восстанавливает связь (§5.4), запрос ждёт её в пределах срока.
3. Сервер доставляет запрос телефону; пока нет подтверждения доставки (нет связи, мёртвое
   соединение), запрос ждёт в очереди со сроком жизни, равным остатку ожидания; телефон получит его,
   когда приложение вернётся на экран (§7).
4. Пользователь отвечает в приложении после входа (§2, Mobile). Ответ идёт на ПК, хук возвращает
   решение агенту. До `resolved` карточка — «отправлено, ждём ПК»; первый `resolved` по запросу
   окончательный.
5. **Срок.** Ответа нет за время ожидания Pult (§2) — хук возвращает «нет решения», агент показывает обычный
   диалог (в desktop-приложении — оставляет уже показанный). Телефону уходит «истёк», карточка гаснет.
6. **Переключение в режим ПК** отпускает ждущие запросы в обычный диалог, телефону уходит «решено на ПК».
   Запрос, решение которого уже передано хуку, и здесь, и при сроке и разрыве закрывается по
   подтверждению хука (при разрыве — без итога телефону); явный отказ хука — «не взял», итог «истёк»;
   обрыв канала или пропажа хука — итог «неизвестен»: действие могло выполниться.
7. **Ответ на ПК.** Ответ в обычном диалоге агент хуку не сообщает и хук не снимает (F-7). Desktop видит его
   сам — разрешение по `PostToolUse` того же инструмента, отказ по записям транскрипта, — отпускает хук с «нет
   решения» и закрывает запрос «решено на ПК» (D-17). Решение телефона хуку после этого не передаётся.
8. **Исход фиксирует desktop** — первым из ответа телефона, срока, переключения в режим ПК, ответа или ввода
   на ПК (п. 7, «Ответ текстом»; итог «решено на ПК») и разрыва. Ответ принят, только когда хук подтвердил, что взял решение.
   Остальные ответы и ответы на неизвестный идентификатор ПК отвергает и сообщает телефону итог (для
   неизвестного — «истёк»).

Вопросы с вариантами идут тем же путём, если адаптер агента умеет передать ответ без участия
интерфейса. Не умеет — хук сразу возвращает «нет решения», при маршруте на телефон вопрос показывается
там только карточкой без действий (отметка — §5.2).

**Ответ текстом.** Агент закончил ход в треде сессии — хук окончания хода в режиме «управление с
телефона» ждёт текст, только пока поток телефона открыт (§4): закрыт сразу или закрылся во время
ожидания — хук отпускает ход (D-58); текст, принятый сервером до закрытия, до хука доходит (§4), а при
связи ПК, пропавшей дольше порога, остаётся на телефоне черновиком (IMPLEMENTATION, этап 3). В остальном
путь запроса (маршрут, срок, исход по п. 2–8, закрытие потока — повод исхода наравне со сроком), но окно не
ждёт ни в очереди (п. 3), ни восстановления связи (п. 2; вход ПК в пределах порога — §4), а отметка — «ждёт текста» вместо «ждёт действия».
Тред на телефоне показывает «ждёт текста» на время окна и «окно закрыто» после.
Текст пришёл — хук отдаёт его агенту как продолжение, тред идёт дальше. Срок, переключение в режим ПК или
разрыв — хук отпускает ход, агент ждёт ввода на ПК как обычно.
Ввод, вставший в очередь агента во время ожидания, отпускает окно сразу: хук не прерывается и о нём не
узнаёт, но запись `enqueue` появляется в транскрипте треда (F-12, F-19). Ввод на ПК побеждает (D-31); так же
окно отпускает сообщение другого треда — например, дочернего оркестратору (D-58): хук отпускает ход, текст
телефона отвергается, телефону — «решено на ПК». Текст, который хук уже взял, агент выполняет первым,
ввод из очереди — следующим ходом.
Агент принимает ограниченное число продолжений подряд и следующее отбрасывает (F-15). Окно, продолжение из
которого превысило бы предел, не открывается: хук сразу отпускает ход, телефон видит «окно закрыто» (D-61).

### 5.4. Конец сессии и отвязка

Сессия = пара. Рвётся с обеих сторон только по одному из поводов: N без событий тредов сессии в любом
режиме (любой хук, включая начало и конец треда); кнопка «Разорвать» на ПК; отвязка с телефона (или
удаление пары без `hello`); успешное новое сопряжение; ПК без связи с сервером дольше 5 минут (сон, сеть,
перезапуск, падение) — сервер удаляет пару и закрывает соединения, ПК считает её разорванной сам;
восстановил раньше — сессия и режим сохраняются. N задаётся в desktop до показа QR — от 15 минут до 36
часов, по умолчанию 4 часа — и фиксирован на всю сессию. Простой отсчитывает только ПК; действия телефона
его не продлевают. Телефон о разрыве узнаёт при подключении. Закрытие последнего треда сессию не рвёт.
Новая сессия — новый QR и новые ключи.

Рвущая сторона удаляет пару на сервере подписанным запросом с причиной; сервер сообщает причину второй стороне
и закрывает соединения (отдельного сообщения `unpair` нет, D-77). Обе стороны стирают ключи пары, телефон — ленты, ждущие запросы уходят в обычный
диалог, как при переключении в режим ПК, но без итога телефону. Причину удаления пары (запрос стороны,
ПК без связи) сервер хранит ограниченный срок и отдаёт стороне при входе; она видна серверу (D-50). Сторона
получает её или, после срока, «пары нет» — и сообщает человеку причину или «разорвала другая сторона».

## 6. Протокол

### 6.1. Конверт

Снаружи — только то, что нужно серверу: версия, пара, отправитель, идентификатор сообщения, время, срок
жизни. Внутри — тип и содержимое, зашифрованные ключом направления из общего ключа пары. Открытые
поля и направление аутентифицируются вместе с содержимым. Идентификаторы сообщений и запросов уникальны
на всю сессию; повторно полученное сообщение подтверждается и не применяется, и память обработанных переживает перезапуск обеих сторон. Время
получатель с часами не сверяет, срок жизни соблюдает сервер и обрезает его сверху. Нерасшифровавшиеся
сообщения отбрасываются, получатель показывает сводную карточку, пара не рвётся; о чужих попытках входа в
пару сервер шлёт ПК и телефону служебный сигнал без текста (они показывают фиксированную фразу с пометкой «от
сервера»), ограничивает попытки по частоте, пару не рвёт.

### 6.2. Доставка

- Сервер подтверждает приём конверта, получатель — доставку.
- Недоставленное лежит на сервере до истечения срока жизни, очередь на пару ограничена, порядок в ней
  сохраняется, при переполнении сервер отказывает в приёме. `thread`, `feed`, `snapshot` и `mode` идут с
  нулевым сроком жизни, мимо очереди.
- Сообщения одной стороны доходят до получателя в порядке отправки по обоим путям — через очередь и мимо
  неё.

### 6.3. Типы сообщений

| Тип | Направление | Смысл |
|---|---|---|
| `hello` | оба | версия, возможности стороны |
| `snapshot` | ПК → телефон | снимок (§5.2) |
| `thread` | ПК → телефон | описание треда: название, статус, родитель, «стоит в диалоге на ПК» |
| `feed` | ПК → телефон | новые записи ленты: сообщения, вызовы инструментов (вывод обрезан) |
| `permission_request` / `permission_response` | ПК ↔ телефон | запрос разрешения и ответ |
| `choice_request` / `choice_response` | ПК ↔ телефон | вопрос с вариантами и ответ |
| `text_request` / `text_response` | ПК ↔ телефон | конец хода: ожидание текста и текст |
| `resolved` | ПК → телефон | запрос закрыт: отвечен, истёк, решён на ПК, неизвестен |
| `mode` | ПК → телефон | текущий режим управления |

Всё телефон рисует одной карточкой общего формата с необязательными действиями; неизвестный тип —
карточка без действий. Так ПК можно обновлять раньше телефона. Новые типы добавляются в `protocol` с
возможностью в `hello`; без объявленной телефоном возможности запрос нового типа не шлётся, хук сразу
возвращает «нет решения».

### 6.4. Версии

Номер версии протокола в конверте и в `/info`. `/info` проверяет совместимость с сервером, совместимость
ПК и телефона — версия в QR и `hello`; несовместимость показывается человеку на обеих сторонах.
Отвергнув `hello` телефона по версии, сервер шлёт ПК служебный сигнал «телефон несовместим»; ПК
показывает его и считает версии несовместимыми (§5.3 п. 2).
Предыдущая версия в MVP не поддерживается.

## 7. Без уведомлений

Пушей и уведомлений нет: ни системных, ни звука, ни вибрации. Пользователь сам наблюдает за тредами в
приложении на экране — события приходят потоком SSE (§4), список тредов показывает отметки (§1).

- Свёрнутое приложение и погасший экран — то же, что закрытое: фоновой службы и постоянного уведомления
  нет (D-52). Уходя с экрана, приложение закрывает поток, дождавшись подтверждения приёма своих `POST` (повтор неподтверждённых —
  IMPLEMENTATION, этап 2); вернувшись — переподключается, шлёт `hello` и получает снимок с открытыми запросами и исходами закрытых (§5.2). Для desktop и сервера
  «приложение на экране» — «поток телефона открыт» (§4, D-60, F-8). Запросы ждут на ПК и
  в очереди сервера в пределах срока. Живость потока — §4.
- Пуши при закрытом приложении спроектированы и отложены на неопределённый срок (§11).

## 8. Самостоятельное развёртывание

Сервер ставится одной командой с автоматическим TLS. Исходящих запросов не делает (§2, Server).

## 9. Ограничения

- Пока приложение не на экране (закрыто, свёрнуто, экран погас), пользователь о запросах не узнаёт: агент
  стоит до конца ожидания Pult (§2) и уходит в обычный диалог на ПК. Работа с телефона — с приложением на экране (§7).
- Пока запрос ждёт телефон, агент на ПК стоит. Ожидание ограничено настройкой, после него — обычный
  диалог на ПК; в desktop-приложении Claude Code диалог на ПК доступен всё время ожидания (§5.3 п. 1).
- В desktop-приложении Claude Code при почти одновременном ответе на ПК и с телефона действует тот ответ, который
  увидели первым: ответ на ПК — desktop отпускает хук, поздний ответ телефона не применяется; ответ телефона —
  диалог на ПК закрывается (F-20).
- Удалённого отзыва нет. Украденный телефон, вошедший по биометрии или PIN, управляет до «Разорвать» или
  простоя, а его ответы двигают агента, и события агента сдвигают отсчёт простоя (§5.4). Утечка закрытого ключа раскрывает одну
  сессию.
- Разрыв на телефоне без связи (отвязка, удаление пары без `hello`, новое сопряжение) ПК не видит и
  держит сессию до «Разорвать» или простоя, которого при работающем агенте нет: каждый запрос с
  телефона ждёт срок и уходит в обычный диалог.
- В сессию попадает любой тред в отмеченной папке, в том числе запущенный не из Pult, и worktree внутри
  неё; тред вне отмеченных папок (например, дочерний в worktree снаружи) остаётся на ПК: его запросы уходят
  в обычный диалог на ПК, а родитель на телефоне показывает «работает» (§5.2). Тред CLI, начатый, когда
  desktop не работал, определяется по каталогу транскрипта, где путь к папке искажён (F-17): папка, которая
  сводится к отмеченной неоднозначно, оставляет тред на ПК. Перенос треда в другую папку — для Pult новый
  тред (D-59).
- Обрыв потока телефона или ПК дольше порога (§4) закрывает окна текста; запросы ждут в очереди.
- Текст — только в окне ожидания конца хода: прервать агента или начать новый тред с телефона нельзя.
  Окно есть, только пока приложение на экране (D-58, §7). Сообщение дочернего треда, вставшее в очередь
  агента, окно оркестратора отпускает (§5.3); то, что агент доставляет не через очередь во время ожидания,
  ждёт конца окна.
- Лента выносит на телефон код и вывод инструментов, зависит от формата транскрипта агента и после
  обрыва связи может иметь пропуски (§5.2).
- Возможности управления ограничены тем, что агент даёт через хуки. Чего нет в хуках, Pult не делает:
  вопрос, который приложение агента задаёт своими кнопками, а не через хук (например, вопрос дочернего
  треда в конце хода в desktop-приложении Claude Code), на телефоне не виден и не отвечается.
- Claude Code принимает ограниченное число продолжений хуком окончания хода подряд (F-15, по умолчанию 8):
  на пределе окна текста нет, следующий ответ — на ПК (D-61).
- После отказа или прерывания хода на ПК агент не вызывает ни одного хука (F-7): тред на телефоне показывает
  «работает» до следующего события треда (D-91); после перезапуска desktop так же держится отметка «стоит в диалоге
  на ПК» у запроса, отклонённого на ПК (`protocol/MESSAGES.md` §6.6).
- Формат транскрипта меняется с версиями агента: после обновления часть ленты может не распознаваться до
  обновления адаптера.

## 10. Этапы

1. **Сквозной прототип:** хук запроса разрешения и хук окончания хода с текстом → desktop → сервер →
   телефон → ответ; чтение транскрипта треда с открытым запросом (ответ и ввод на ПК), отпускание хука при
   ответе на ПК; без шифрования и подписи, пара задаётся вручную. Проверяет гипотезы о хуках и транскрипте
   (итоги — FACTS.md) и закрытие потока SSE при уходе приложения с экрана.
2. Ключи, сопряжение по QR, шифрование, подпись `POST` и вход, версии.
3. Статусы, лента, снимок, переключатель режима, жизненный цикл сессии, вопросы с вариантами, ответ
   текстом.
4. Установка сервера одной командой, README, страница на сайте, APK в GitHub Releases.

## 11. Отложено на неопределённый срок

Решение владельца 06.11.2026: пуши и публикация в RuStore отложены (транспорт — SSE, действует, §4). Идеи
сохранены ниже в том виде, в каком были спроектированы; решения — в разделе «Отложенные» реестра
`DECISIONS.md` (D-8, D-10, D-27, D-38), детали реализации — в разделе «Отложено» `IMPLEMENTATION.md`.

### 11.1. Push-gateway — пятый блок

| Блок | Что делает | Кто разворачивает |
|---|---|---|
| `push-gateway` | будит телефон через пуш-провайдера | только мы |

Хранит связку «непрозрачный идентификатор устройства → пуш-токен провайдера» и по запросу сервера шлёт
пустое пробуждение. Провайдер — RuStore Push; добавление провайдера — новая реализация за общим
интерфейсом. Форк приложения требует своего шлюза и своего проекта у пуш-провайдера.

### 11.2. Пуши

1. Адрес шлюза зашит в сборку приложения.
2. Телефон регистрирует свой пуш-токен в шлюзе подписанным запросом и получает непрозрачный идентификатор
   устройства. Идентификатор живёт одну сессию, при разрыве телефон его удаляет (без связи — при первой
   связи после разрыва).
3. Серверу телефон отдаёт только адрес шлюза и этот идентификатор.
4. Сервер будит телефон запросом в шлюз с идентификатором. Пуш пустой: проснувшись, телефон забирает
   сообщения с сервера.
5. Шлюз ограничивает частоту пробуждений на идентификатор и на источник, принимает пробуждения только
   для зарегистрированных идентификаторов.

API шлюза публичный и стабильный: в него ходят серверы, которые мы не контролируем.

### 11.3. Что возвращается в остальные разделы вместе с пушами

- §1: «пробуждение телефона пушем, когда нужно действие»; сервер будит через шлюз из своего списка.
- §2: сервер будит телефон через шлюз из своего списка, лимит пробуждений на пару.
- §5.1, шаг 6: телефон регистрируется в шлюзе и сообщает серверу адрес шлюза и свой идентификатор там;
  не удалось — повтор при каждом запуске, до успеха обе стороны показывают «без пушей» (пробуждение —
  возможность в `hello`).
- §5.3: нет подтверждения доставки в срок — телефон будится. Системные уведомления — без содержимого
  запроса и ленты (включая название из первого сообщения), на заблокированном экране — только
  «Pult: нужно действие», без названия треда. Вопрос, который адаптер не умеет передать, — уведомление,
  которое будит телефон. Ожидание текста телефон не будит.
- §6.1: признак «будить телефон» в открытых полях конверта.
- §8: сервер будит только через шлюзы из списка, заданного при развёртывании, по умолчанию — наш. Наш
  шлюз видит сервер-источник, устройство и время пробуждений, но не содержимое.
- §9: шлюз — общая точка отказа пушей; пуш через RuStore требует приложения RuStore на телефоне;
  агрессивная экономия батареи у части производителей задерживает пуши, онбординг показывает, где
  разрешить работу в фоне.
- §4: для пробуждения через шлюз транспорт не меняется; спроектировано было на WebSocket.
- §10: этап «Шлюз и RuStore Push» перед установкой сервера.

### 11.4. Публикация в RuStore

Распространение через RuStore вместо или вместе с APK в GitHub Releases. Пуши RuStore требуют проекта в
консоли RuStore (F-4).
