# Pult — архитектура и протокол

Pult — пульт для ИИ-агентов на ПК: телефон показывает, что делают треды агента (Claude Code, OpenCode
и другие), и позволяет ответить на запрос разрешения, вопрос с вариантами или продолжить тред текстом, не
подходя к компьютеру.

## 1. Границы

**Входит:**
- лента тредов на телефоне (сообщения агента и пользователя, вызовы инструментов, запросы) со статусом
  (работает, закончил, ошибка) и отметками «ждёт действия», «ждёт текста»;
- ответ с телефона на запрос разрешения и вопрос с вариантами (если адаптер умеет), ответ текстом в конце
  хода агента;
- самостоятельное развёртывание сервера-реле.

**Не входит (MVP):**
- захват экрана и имитация кликов;
- веб-панель и учётные записи;
- прерывание агента посреди хода, новый тред с телефона, ход рассуждений модели в ленте;
- iOS в эксплуатации: собирается, но не проверяется и не публикуется;
- пуши, системные уведомления, звук и вибрация: пользователь сам смотрит в открытое приложение (§7);
- публикация в RuStore — отложена на неопределённый срок (§11).

## 2. Компоненты

Монорепозиторий, лицензия MIT, четыре блока.

| Блок | Что делает | Кто разворачивает |
|---|---|---|
| `protocol` | спецификация, схемы сообщений, эталонные векторы криптографии | — |
| `desktop` | фоновое приложение в трее + хуки агентов | пользователь на своём ПК |
| `server` | реле: соединения, маршрутизация, очередь недоставленного | мы или пользователь где угодно |
| `mobile` | приложение KMP + Compose Multiplatform | только мы, APK в GitHub Releases |

### Desktop

- **Фоновое приложение** держит ключи ПК, соединение с сервером и состояние тредов. Отвечает хукам
  по локальному каналу, недоступному другим учётным записям ПК, и только по локальному секрету установки.
- **Окно desktop** — переключатель режима «управление с телефона» / «управление с ПК» (§5.3), кнопка
  «Разорвать» и новый QR (§5.4). Режим меняется только здесь; сессия стартует в режиме «с телефона» и
  сохраняет его при восстановлении связи (§5.4).
- **Хуки** — короткие скрипты на события агента. Сами по сети не ходят: передают событие фоновому
  приложению и, если событие блокирующее, ждут его ответа. Если агент умеет слать событие хука запросом
  на локальный адрес сам (у Claude Code — HTTP-хуки), скрипт не нужен; выбор — по итогу этапа 1, от него
  зависит, кто отсчитывает срок ожидания (F-6).
- **Адаптеры агентов** приводят события, транскрипт треда (фоновое приложение читает его по мере записи)
  и данные агента о тредах (название, продолжение, форк, родитель) к общим типам протокола. Новый агент —
  новый адаптер, ядро не меняется. Формат транскрипта агент не обещает держать (F-10): запись, которую
  адаптер не понял, пропускается, лента получает пометку «часть записей не распознана», статусы и
  запросы идут от хуков и от этого не зависят.
- Фоновое приложение не запущено или связь с ним оборвалась — хук сразу возвращает «нет решения», агент
  показывает свой обычный диалог. Pult никогда не блокирует агента дольше настроенного ожидания: срок
  отсчитывает сам хук, независимо от фонового приложения, и он меньше таймаута хука у агента.

### Server

Тупое реле. Знает пары и открытые ключи, пересылает зашифрованные конверты, хранит недоставленные до
истечения их срока. Содержимое не видит и не может подделать. Исходящих запросов не делает.
Ограничивает число заявок и пар с одного адреса, срок хранения, размер конвертов и трафик.

### Mobile

Хранит одну сессию (сервер, пара, ключи ПК), держит соединение, пока открыто, показывает ленты тредов
карточками общего формата (§6.3). Треды сессии — списком в навбаре со статусом и отметкой «ждёт действия»
или «ждёт текста». Название присылает desktop: из данных агента, иначе первое
сообщение и папка проекта.

## 3. Ключи и доверие

- Алгоритм — **P-256**: ECDSA для подписи, ECDH для общего ключа. Причина — аппаратное хранилище на обеих
  мобильных платформах.
- У каждой стороны две пары ключей: подпись и согласование. Закрытые не покидают устройство (телефон —
  Android Keystore, ПК — хранилище ОС), сервер хранит только открытые.
- Общий ключ пары — из согласования ключей ПК и телефона. Им шифруются и аутентифицируются все
  сообщения пары. Сервер его вычислить не может.
- Ключи ПК телефон берёт из QR, ключи телефона ПК проверяет по одноразовому секрету из QR, которого
  сервер не получает (§5.1). Сверка отпечатка — дополнительная защита.

## 4. Транспорт

- HTTPS до сервера у ПК и у телефона, одна схема для обоих: события от сервера — поток SSE, свои
  сообщения — HTTP-запросы `POST`. Подтверждение приёма — ответ на `POST`, подтверждение доставки —
  отдельный `POST` получателя (§6.2).
- Вход по принципу «вызов — ответ»: сервер присылает случайное значение, клиент подписывает его ключом
  подписи и открывает поток. Каждый `POST` подписан ключом подписи и привязан к открытому потоку;
  долгоживущих токенов нет.
- Поток оборвался — клиент переподключается сам; пропущенное за время обрыва приходит снимком (§5.2) и из
  очереди сервера (§6.2).
- `GET /info` сервера отдаёт поддерживаемые версии протокола; клиент проверяет их до сопряжения и при
  каждом подключении (§6.4).

## 5. Сценарии

### 5.1. Сопряжение

1. Пользователь ставит desktop и задаёт адрес сервера (по умолчанию — наш).
2. Desktop создаёт ключи, регистрирует на сервере одноразовую заявку и показывает QR: адрес сервера,
   идентификатор заявки, одноразовый секрет, открытые ключи ПК, версия протокола, срок простоя (§5.4).
   Серверу уходят заявка и открытые ключи ПК, секрет — никогда. До показа QR, как и срок, пользователь
   выбирает треды сессии из последних по активности (по умолчанию 5, отмечены все); созданные после
   сопряжения входят сами.
3. Телефон сканирует QR, создаёт свои ключи, заверяет их секретом и отправляет на сервер вместе с
   идентификатором заявки.
4. Сервер передаёт ПК ключи телефона. Заявка сгорает; повторный скан показывает «QR уже использован,
   нужен новый на ПК».
5. ПК проверяет заверение. Сошлось — сессия за тем, кто отсканировал первым: пара активна, QR исчезает,
   ПК шлёт `hello`; без него телефон за время жизни заявки удаляет пару. Не сошлось — новая пара
   удаляется, ПК сообщает о попытке и предлагает новый QR. Отпечаток — для дополнительной сверки.

`hello` телефон шлёт при каждом подключении и при изменении возможностей.

Строго один ПК и один телефон; несколько ПК или серверов на телефоне не поддерживаются. Успешное новое
сопряжение на любой стороне — обычный разрыв прежней сессии этой стороны (§5.4).

### 5.2. Статус и лента треда

Хук сообщает событие, адаптер — новые записи транскрипта → фоновое приложение обновляет статус и ленту
треда → отправляет на телефон, если он подключён. Пользователь видит их, пока приложение
открыто (§7).
На `hello` телефона и после своего подключения ПК шлёт снимок: треды с лентами, открытые запросы и режим.
С карточек, которых нет в снимке, телефон снимает действия; запрос, которого нет в снимке, закрыт, а без
`resolved` его исход — «неизвестен», пока `resolved` не придёт. После долгого отсутствия связи снимок
дополняет имеющуюся ленту, на стыке — пометка «пропущены записи». Снимок и лента — только о тредах
сессии: тред появляется с первого своего события после сопряжения, история до сопряжения не передаётся.
Тред с новым идентификатором (продолжение, форк, очистка контекста) входит в сессию, только если в ней
исходный (это правило старше «созданные после сопряжения входят сами»). Продолжение — та же лента и тот
же пункт списка, форк — отдельный пункт «форк …»; не определилось родство — тред вне сессии и остаётся на
ПК.

**Дочерние треды.** Тред, который запустил другой тред (оркестратор → дочерний), входит в сессию, только
если в ней родитель, — по тому же правилу старшинства, что продолжение. В списке он стоит под родителем;
у родителя видна сводная отметка «ждёт действия» или «ждёт текста», если она есть хоть у одного
дочернего. Сообщения между тредами — записи ленты обоих тредов с пометкой, от какого треда. Запросы и
ожидание текста у дочернего треда — как у любого (§5.3). Родителя адаптер берёт из данных агента;
не определился — тред считается самостоятельным и входит в сессию по общим правилам (F-14).

### 5.3. Запрос разрешения, вопрос с вариантами, ответ текстом

1. Агент вызывает блокирующий хук. Хук передаёт запрос фоновому приложению.
2. **Маршрут.** Решает переключатель в окне desktop. Режим «управление с ПК», тред вне сессии, нет
   активной сессии, сервер явно отказал в приёме, несовместимы версии по последнему
   `hello` (§6.4) — хук сразу возвращает «нет решения», агент показывает обычный диалог. Иначе запрос
   уходит на телефон; пока desktop восстанавливает связь (§5.4), запрос ждёт её в пределах срока.
3. Сервер доставляет запрос телефону; нет подтверждения доставки в срок (нет связи, мёртвое
   соединение) — запрос ждёт в очереди со сроком жизни, равным остатку ожидания; телефон получит его,
   когда откроют приложение (§7).
4. Пользователь отвечает в приложении, открытом по биометрии или PIN. Ответ идёт на ПК, хук возвращает
   решение агенту. До `resolved` карточка — «отправлено, ждём ПК»; первый `resolved` по запросу
   окончательный.
5. **Срок.** Ответа нет за время ожидания — хук возвращает «нет решения», агент показывает обычный
   диалог. Телефону уходит «истёк», карточка гаснет.
6. **Переключение в режим ПК** отпускает ждущие запросы в обычный диалог, телефону уходит «решено на ПК».
   Запрос, решение которого уже передано хуку, и здесь, и при сроке и разрыве закрывается по
   подтверждению хука (при разрыве — без итога телефону); явный отказ хука — «не взял», итог «истёк»;
   обрыв канала или пропажа хука — итог «неизвестен»: действие могло выполниться.
7. **Исход фиксирует desktop** — первым из ответа телефона, срока, переключения в режим ПК, ввода на ПК
   (итог «решено на ПК») и разрыва. Ответ принят, только когда хук подтвердил, что взял решение.
   Остальные ответы и ответы на неизвестный идентификатор ПК отвергает и сообщает телефону итог (для
   неизвестного — «истёк»).

Вопросы с вариантами идут тем же путём, если адаптер агента умеет передать ответ без участия
интерфейса. Не умеет — хук сразу возвращает «нет решения», при маршруте на телефон вопрос показывается
там только карточкой без действий.

**Ответ текстом.** Агент закончил ход — хук окончания хода в режиме «управление с телефона» ждёт текст с
телефона тем же путём, что запрос (маршрут, очередь, срок, исход по п. 2–7), но с отметкой «ждёт текста»
вместо «ждёт действия». Тред на телефоне показывает «ждёт текста» на время окна и «окно закрыто» после.
Текст пришёл — хук отдаёт его агенту как продолжение, тред идёт дальше. Срок, переключение в режим ПК или
разрыв — хук отпускает ход, агент ждёт ввода на ПК как обычно. Ввод на ПК во время ожидания, если desktop
его видит, побеждает: хук отпускается, текст телефона отвергается; не видит — сначала переключить режим
(по итогу этапа 1).

### 5.4. Конец сессии и отвязка

Сессия = пара. Рвётся с обеих сторон только по одному из поводов: N без событий тредов сессии в любом
режиме (любой хук, включая начало и конец треда); кнопка «Разорвать» на ПК; отвязка с телефона (или
удаление пары без `hello`); успешное новое сопряжение; ПК без связи с сервером дольше 5 минут (сон, сеть,
перезапуск, падение) — сервер удаляет пару и закрывает соединения, ПК считает её разорванной сам;
восстановил раньше — сессия и режим сохраняются. N задаётся в desktop до показа QR — от 15 минут до 36
часов, по умолчанию 4 часа — и фиксирован на всю сессию. Простой отсчитывает только ПК; действия телефона
его не продлевают. Телефон о разрыве узнаёт при подключении. Закрытие последнего треда сессию не рвёт.
Новая сессия — новый QR и новые ключи.

Рвущая сторона шлёт `unpair` с причиной и подписанным запросом удаляет пару на сервере; сервер закрывает
соединения. Обе стороны стирают ключи пары, телефон — ленты, ждущие запросы уходят в обычный диалог, как
при переключении в режим ПК, но без итога телефону. Сторона, которой сервер при входе отвечает «пары
нет», считает сессию разорванной («разорвала другая сторона») и сообщает человеку.

## 6. Протокол

### 6.1. Конверт

Снаружи — только то, что нужно серверу: версия, пара, отправитель, идентификатор сообщения, время, срок
жизни. Внутри — тип и содержимое, зашифрованные общим ключом пары. Открытые
поля и направление аутентифицируются вместе с содержимым. Идентификаторы сообщений и запросов уникальны
на всю сессию; повтор отвергается по ним, и память обработанных переживает перезапуск обеих сторон. Время
получатель с часами не сверяет, срок жизни соблюдает сервер и обрезает его сверху. Нерасшифровавшиеся
сообщения отбрасываются со сводным уведомлением, пара не рвётся; о чужих попытках входа в пару сервер
шлёт ПК и телефону служебный сигнал без текста (они показывают фиксированную фразу с пометкой «от
сервера»), ограничивает попытки по частоте, пару не рвёт.

### 6.2. Доставка

- Сервер подтверждает приём конверта, получатель — доставку.
- Недоставленное лежит на сервере до истечения срока жизни, очередь на пару ограничена, порядок в ней
  сохраняется, при переполнении сервер отказывает в приёме. `status`, `feed`, `snapshot` и `mode` идут с
  нулевым сроком жизни, мимо очереди.

### 6.3. Типы сообщений

| Тип | Направление | Смысл |
|---|---|---|
| `hello` | оба | версия, возможности стороны |
| `snapshot` | ПК → телефон | снимок (§5.2) |
| `status` | ПК → телефон | изменение статуса треда |
| `feed` | ПК → телефон | новые записи ленты: сообщения, вызовы инструментов (вывод обрезан) |
| `permission_request` / `permission_response` | ПК ↔ телефон | запрос разрешения и ответ |
| `choice_request` / `choice_response` | ПК ↔ телефон | вопрос с вариантами и ответ |
| `text_request` / `text_response` | ПК ↔ телефон | конец хода: ожидание текста и текст |
| `resolved` | ПК → телефон | запрос закрыт: отвечен, истёк, решён на ПК, неизвестен |
| `notification` | ПК → телефон | информационное событие без действия |
| `mode` | ПК → телефон | текущий режим управления |
| `unpair` | оба | разрыв пары с причиной |

Всё телефон рисует одной карточкой общего формата с необязательными действиями; неизвестный тип —
карточка без действий. Так ПК можно обновлять раньше телефона. Новые типы добавляются в `protocol` с
возможностью в `hello`; без объявленной телефоном возможности запрос нового типа не шлётся, хук сразу
возвращает «нет решения».

### 6.4. Версии

Номер версии протокола в конверте и в `/info`. `/info` проверяет совместимость с сервером, совместимость
ПК и телефона — версия в QR и `hello`; несовместимость показывается человеку на обеих сторонах.
Отвергнув `hello` телефона по версии, сервер шлёт ПК служебный сигнал «телефон несовместим»; ПК
показывает его и считает версии несовместимыми (§5.3 п. 2).
Предыдущая версия в MVP не поддерживается.

## 7. Без уведомлений

Пушей и уведомлений нет: ни системных, ни звука, ни вибрации. Пользователь сам наблюдает за тредами в
открытом приложении — события приходят потоком SSE (§4), список тредов показывает отметки «ждёт
действия» и «ждёт текста».

- Приложение свёрнуто или экран погас — поток может закрыться (F-8). Запросы ждут на ПК и в очереди
  сервера в пределах срока; при открытии приложения телефон получает их снимком (§5.2), истёкшие — итогом.
- Пуши при закрытом приложении спроектированы и отложены на неопределённый срок (§11).

## 8. Самостоятельное развёртывание

Сервер ставится одной командой с автоматическим TLS. Исходящих запросов не делает: развёртывание не
требует ключей пуш-провайдера и списка шлюзов.

## 9. Ограничения

- Пока приложение закрыто, телефон о запросах не узнаёт: агент стоит до срока ожидания и уходит в
  обычный диалог на ПК. Работа с телефона — с открытым приложением.
- Пока запрос ждёт телефон, агент на ПК стоит. Ожидание ограничено настройкой, после него — обычный
  диалог на ПК.
- Удалённого отзыва нет. Украденный телефон, вошедший по биометрии или PIN, управляет до «Разорвать» или
  простоя, а его ответы двигают агента и тем продлевают простой. Утечка закрытого ключа раскрывает одну
  сессию.
- Разрыв на телефоне без связи (отвязка, удаление пары без `hello`, новое сопряжение) ПК не видит и
  держит сессию до «Разорвать» или простоя, которого при работающем агенте нет: каждый запрос с
  телефона ждёт срок и уходит в обычный диалог.
- Текст — только в окне ожидания конца хода: прервать агента или начать новый тред с телефона нельзя.
  Окно длится срок запроса, поэтому без открытого приложения пропускается.
- Лента выносит на телефон код и вывод инструментов, зависит от формата транскрипта агента и после
  долгого отсутствия связи может иметь пропуски.
- Возможности управления ограничены тем, что агент даёт через хуки. Чего нет в хуках, Pult не делает:
  вопрос, который приложение агента задаёт своими кнопками, а не через хук (например, вопрос дочернего
  треда в конце хода в desktop-приложении Claude Code), на телефоне не виден и не отвечается.
- Ответ текстом держит ход открытым: Claude Code снимает хук окончания хода после 8 продолжений подряд
  без вызова инструментов (F-9). Дальше ход заканчивается, текст вводится на ПК.
- Формат транскрипта меняется с версиями агента: после обновления часть ленты может не распознаваться до
  обновления адаптера.

## 10. Этапы

1. **Сквозной прототип:** хук запроса разрешения и хук окончания хода с текстом → desktop → сервер →
   телефон → ответ, чтение транскрипта; без шифрования. Проверяет гипотезы о хуках и транскрипте,
   включая путь без ответа, источник названия треда, ввод на ПК во время ожидания, родство тредов,
   дочерние треды, HTTP-хук против скрипта и поток SSE в свёрнутом приложении.
2. Ключи, сопряжение по QR, шифрование, версии.
3. Статусы, лента, снимок, переключатель режима, жизненный цикл сессии, вопросы с вариантами, ответ
   текстом.
4. Установка сервера одной командой, README, страница на сайте, APK в GitHub Releases.

## 11. Отложено на неопределённый срок

Решение владельца 06.11.2026: пуши и публикация в RuStore отложены, транспорт — SSE вместо WebSocket. Идеи
сохранены ниже в том виде, в каком были спроектированы; решения — в разделе «Отложенные» реестра
`DECISIONS.md` (D-8, D-10, D-27, D-38), детали реализации — в разделе «Отложено» `IMPLEMENTATION.md`.

### 11.1. Push-gateway — пятый блок

| Блок | Что делает | Кто разворачивает |
|---|---|---|
| `push-gateway` | будит телефон через пуш-провайдера | только мы |

Хранит связку «непрозрачный идентификатор устройства → пуш-токен провайдера» и по запросу сервера шлёт
пустое пробуждение. Провайдер — RuStore Push; добавление провайдера — новая реализация за общим
интерфейсом. Форк приложения требует своего шлюза и своего проекта у пуш-провайдера.

### 11.2. Пуши

1. Адрес шлюза зашит в сборку приложения.
2. Телефон регистрирует свой пуш-токен в шлюзе подписанным запросом и получает непрозрачный идентификатор
   устройства. Идентификатор живёт одну сессию, при разрыве телефон его удаляет (без связи — при первой
   связи после разрыва).
3. Серверу телефон отдаёт только адрес шлюза и этот идентификатор.
4. Сервер будит телефон запросом в шлюз с идентификатором. Пуш пустой: проснувшись, телефон забирает
   сообщения с сервера.
5. Шлюз ограничивает частоту пробуждений на идентификатор и на источник, принимает пробуждения только
   для зарегистрированных идентификаторов.

API шлюза публичный и стабильный: в него ходят серверы, которые мы не контролируем.

### 11.3. Что возвращается в остальные разделы вместе с пушами

- §1: «пробуждение телефона пушем, когда нужно действие»; сервер будит через шлюз из своего списка.
- §2: сервер будит телефон через шлюз из своего списка, лимит пробуждений на пару.
- §5.1, шаг 6: телефон регистрируется в шлюзе и сообщает серверу адрес шлюза и свой идентификатор там;
  не удалось — повтор при каждом запуске, до успеха обе стороны показывают «без пушей» (пробуждение —
  возможность в `hello`).
- §5.3: нет подтверждения доставки в срок — телефон будится. Системные уведомления — без содержимого
  запроса и ленты (включая название из первого сообщения), на заблокированном экране — только
  «Pult: нужно действие», без названия треда. Вопрос, который адаптер не умеет передать, — уведомление,
  которое будит телефон. Ожидание текста телефон не будит.
- §6.1: признак «будить телефон» в открытых полях конверта.
- §8: сервер будит только через шлюзы из списка, заданного при развёртывании, по умолчанию — наш. Наш
  шлюз видит сервер-источник, устройство и время пробуждений, но не содержимое.
- §9: шлюз — общая точка отказа пушей; пуш через RuStore требует приложения RuStore на телефоне;
  агрессивная экономия батареи у части производителей задерживает пуши, онбординг показывает, где
  разрешить работу в фоне.
- §4: для пробуждения через шлюз транспорт не меняется; спроектировано было на WebSocket.
- §10: этап «Шлюз и RuStore Push» перед установкой сервера.
