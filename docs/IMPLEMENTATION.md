# Детали реализации по этапам

Детали, которые решаются в коде, а не в архитектуре. Этапы — §10 ARCHITECTURE.md.

## Этап 1 — сквозной прототип
- [x] Локальный канал хука недоступен другим учётным записям Windows; на loopback (D-54) — секрет установки и
      проверка скриптом хука до передачи события, что порт держит наше фоновое приложение (агент этого не
      проверяет: процесс, занявший порт раньше, получил бы событие с секретом). Сделано: хук — `PultHook.exe`, шлёт
      событие, только если порт держит `Pult.exe` из той же папки, с секретом `hook-secret.txt`.
- [x] Ответ хука агенту — UTF-8 в stdout независимо от кодировки консоли (F-9).
- [x] Где хранится настройка ожидания Pult и как desktop прописывает таймаут хука в настройках агента; ожидание
      Pult меньше `timeout` хука (по умолчанию 600 с, F-5). Сделано: `wait_seconds` в `settings.txt` (по умолчанию 300,
      от 10 до 540), хук сам отпускает агента через 570 с при `timeout` 600.
- [x] Какие события desktop принимает, кроме блокирующих: `PostToolUse`/`PostToolUseFailure` (ответ на ПК),
      `SessionStart` (папка начала), `StopFailure` (статус «ошибка»); неблокирующие хуки отвечают сразу. `PreToolUse` не нужен:
      он вызывал бы хук на каждый инструмент, а для сопоставления ответа на ПК не требуется.
- [ ] (этап 3) Признак треда desktop-приложения Claude Code — переменная `CLAUDE_CODE_HOST_SESSION_ID` в окружении
      хука: у такого треда диалог на ПК показан сразу, отметка «стоит в диалоге на ПК» — с первой секунды (D-34).
- [x] Отпускание хука при ответе на ПК (D-17): у `PermissionRequest` нет `tool_use_id` — запрос сопоставляется
      с `PostToolUse` по порядку и `tool_input`; отказ — по записям транскрипта (результат инструмента с
      отказом пользователя и `[Request interrupted by user for tool use]`), событий хуков после него нет.
      Разрешение на ПК отпускает хук за 0,1–0,2 с; отказ на ПК проверен только подставленным событием.
- [x] Слежение за транскриптом треда (`transcript_path` события), пока у него открыт запрос или окно текста:
      записи отказа на ПК и `queue-operation` `enqueue` (ввод на ПК — D-31, сообщение другого треда — D-58)
      отпускают хук; задержка от записи до отпускания.
- [x] Счёт продолжений подряд по `stop_hook_active` и предел из окружения хука (D-61).
- [ ] (этап 3) Папка начала треда (D-59): `originCwd` из метаданных треда desktop-приложения по
      `CLAUDE_CODE_HOST_SESSION_ID`; `cwd` из `SessionStart` (`startup`), которые desktop запоминает и вне
      сессии; иначе каталог транскрипта — сравнение искажённого пути с отмеченными папками и признак
      неоднозначности.
- [ ] F-20: что агент делает с ответом хука после ответа на ПК; от итога зависит ограничение §9.
- [x] Схема SSE + `POST` без подписи, пара задаётся вручную (`protocol/README.md`; токены сторон в `pairs.json`,
      пара — командой `add-pair`).
- [x] Подтверждение доставки — отдельный `POST` получателя (`acks`); неподтверждённое на открытом потоке повторно не
      шлётся, приходит снова при следующем входе, получатель отбрасывает обработанные `id`.
- [x] Порядок доставки по двум путям сервера (§6.2): единый `seq` на пару, один исходящий порядок на поток.
- [x] У стороны один поток: новый вход закрывает прежний. Порог «поток без признаков жизни» (§4) — 45 с, `ping` раз в
      15 с, любой авторизованный `POST` — признак жизни; обрыв TCP сервер видит за доли секунды. Приложение,
      уходя с экрана, ждёт подтверждения своих `POST` до 2 с, затем закрывает поток.
- [ ] Закрытие потока при уходе приложения с экрана; как быстро его видят сервер и desktop (F-8). Сигнал о потоке
      телефона идёт после всех принятых от него сообщений, при входе ПК — текущее состояние (§4). Штатный уход (Home,
      гашение экрана) замерен на устройстве: сигнал на сервере через ~0,5 с. Не проверено: путь через Caddy и заморозка
      процесса до `onStop` (тогда — порог 45 с).
- [ ] На этапе 1 снимка нет: карточки живут в памяти процесса приложения и при его убийстве восстанавливаются только
      из очереди сервера; снимок — этап 3 (§5.2).
- [ ] Свои хуки рядом с хуками AgentGlow в настройках Claude Code: установка и удаление не трогают чужие.
- [ ] Сервер на aokaztest.ru за Caddy — путь `/pult/` (без новой записи DNS и сертификата), реле на 127.0.0.1:8082,
      `flush_interval -1`; по правилам стенда stop-фильтр журнала для IP и журналы не дольше 30 дней.
- [x] Порт приёма хуков desktop по умолчанию — 47652 (`hook_port` в `settings.txt`): 47651 занят AgentGlow.

## Этап 2 — ключи, сопряжение, шифрование
- [ ] Подпись каждого `POST`, вход «вызов — ответ» и привязка к открытому потоку SSE; защита от повтора.
- [ ] Проверка подписи P-256 на сервере (Python) — библиотекой из пакетов Ubuntu 22.04.
- [ ] minSdk mobile по F-3.
- [ ] Способ заверения ключей телефона для ПК (одноразовый секрет в QR / фиксация до раскрытия), длина отпечатка.
- [ ] Шифрование с аутентификацией открытых полей конверта; разделение направлений (ключи по направлению или
      отправитель в связанных данных), KDF.
- [ ] Срок жизни заявки сопряжения: значение, где задан (в QR или константа протокола), от чего телефон отсчитывает
      ожидание `hello`.
- [ ] Когда поднимается номер версии протокола: новый тип идёт возможностью в `hello` без смены версии, версия
      меняется только при несовместимом изменении конверта.
- [ ] Классы срока жизни служебных сообщений (`resolved`, `unpair`, `hello`, `notification`, сигнал сервера о
      чужой попытке входа) под общим потолком сервера.
- [ ] Карточка «отправлено» на телефоне — по подтверждению приёма сервером; без подтверждения повтор с тем же
      идентификатором.

## Этап 3 — статусы, лента, снимок, сессия
- [ ] Снимок несёт хвост ленты треда, а не всю ленту; размер хвоста; порядковый номер записи ленты в треде для
      поиска стыка.
- [ ] Переподключение потока (`Last-Event-ID` или только снимок; порог и один поток — этап 1) и проверка «после обрыва ничего не пропало».
- [ ] Срок ожидания хука больше N простоя — исход: сессия рвётся раньше, хук отпускает в обычный диалог.
- [ ] Срок хранения причины удаления пары на сервере (D-50); порог повторного входа на телефоне (D-51).
- [ ] Снимок укладывается в лимит размера конверта — хвост ленты и/или части снимка; открытые запросы, исходы
      закрытых, статусы и режим идут обязательно и первыми.
- [ ] Снимок собирается и отправляется в одном упорядоченном потоке с событиями ПК: запрос, созданный во время сборки
      снимка, не попадает «за» снимок и не закрывается им как «неизвестен»; тест на гонку `hello` / запрос.
- [ ] Правила отрисовки недоверенной ленты — подмножество разметки, без загрузки внешних ресурсов, ссылки не
      открываются автоматически.
- [ ] Принятый текст с телефона в ленте — одна реплика (запись транскрипта, карточка ответа её не дублирует);
      отвергнутый или неотправленный текст остаётся у пользователя черновиком.

## Этап 4 — сервер и выпуск
- [ ] Пороги серверных лимитов: заявки и пары с одного адреса, верхняя граница срока жизни конверта.
- [ ] Пороги размера конверта и объёма трафика пары за период.
- [ ] Пары, очередь и причины — на диске; после старта сервер считает «без ПК» (D-26) с момента старта; простой ночной
      перезагрузки стенда вместе с повтором desktop укладывается в 5 минут, иначе — строка в §9.

## Отложено (D-44: пуши и RuStore)
- [ ] Политика стабильности публичного API шлюза: версия в пути, обратная совместимость, предупреждение об
      устаревании.
- [ ] Ограничение частоты пробуждений: на идентификатор и на источник, пороги.
- [ ] Обновление пуш-токена RuStore в шлюзе при его смене провайдером.
- [ ] Каким ключом подписаны регистрация и удаление идентификатора в шлюзе.
- [ ] Срок ожидания подтверждения доставки, после которого сервер будит телефон пушем.
- [ ] После забора сообщений телефон показывает локальное уведомление на каждый открытый запрос, нажатие ведёт в его
      тред.
- [ ] Шлюз сборки не в списке сервера (D-27) — сессия работает без пушей, приложение один раз показывает «сервер не
      будит телефон этой сборки»; повторная регистрация — только при новом сопряжении.
