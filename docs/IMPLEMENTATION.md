# Детали реализации по этапам

Детали, которые решаются в коде, а не в архитектуре. Этапы — §10 ARCHITECTURE.md.

## Этап 1 — сквозной прототип
- [x] Локальный канал хука недоступен другим учётным записям Windows; на loopback (D-54) — секрет установки и
      проверка скриптом хука до передачи события, что порт держит наше фоновое приложение (агент этого не
      проверяет: процесс, занявший порт раньше, получил бы событие с секретом). Сделано: хук — `PultHook.exe`, шлёт
      событие, только если порт держит `Pult.exe` из той же папки, с секретом `hook-secret.txt`.
- [x] Ответ хука агенту — UTF-8 в stdout независимо от кодировки консоли (F-9).
- [x] Где хранится настройка ожидания Pult и как desktop прописывает таймаут хука в настройках агента; ожидание
      Pult меньше `timeout` хука (по умолчанию 600 с, F-5). Сделано: `wait_seconds` в `settings.txt` (по умолчанию 300,
      от 10 до 540), хук сам отпускает агента через 570 с при `timeout` 600.
- [x] Какие события desktop принимает, кроме блокирующих: `PostToolUse`/`PostToolUseFailure` (ответ на ПК),
      `SessionStart` (папка начала), `StopFailure` (статус «ошибка»); неблокирующие хуки отвечают сразу. `PreToolUse` не нужен:
      он вызывал бы хук на каждый инструмент, а для сопоставления ответа на ПК не требуется.
- [x] (этап 3) Признак треда desktop-приложения Claude Code — переменная `CLAUDE_CODE_HOST_SESSION_ID` в окружении
      хука: у такого треда диалог на ПК показан сразу, отметка «стоит в диалоге на ПК» — с первой секунды (D-34).
- [x] Отпускание хука при ответе на ПК (D-17): у `PermissionRequest` нет `tool_use_id` — запрос сопоставляется
      с `PostToolUse` по порядку и `tool_input`; отказ — по записям транскрипта (результат инструмента с
      отказом пользователя и `[Request interrupted by user for tool use]`), событий хуков после него нет.
      Разрешение на ПК отпускает хук за 0,1–0,2 с; отказ на ПК проверен только подставленным событием.
- [x] Слежение за транскриптом треда (`transcript_path` события), пока у него открыт запрос или окно текста:
      записи отказа на ПК и `queue-operation` `enqueue` (ввод на ПК — D-31, сообщение другого треда — D-58)
      отпускают хук; задержка от записи до отпускания.
- [x] Счёт продолжений подряд по `stop_hook_active` и предел из окружения хука (D-61).
- [x] (этап 3) Папка начала треда (D-59): `originCwd` из метаданных треда desktop-приложения по
      `CLAUDE_CODE_HOST_SESSION_ID`; `cwd` из `SessionStart` (`startup`), которые desktop запоминает и вне
      сессии; иначе каталог транскрипта — сравнение искажённого пути с отмеченными папками и признак
      неоднозначности.
- [x] F-20: при почти одновременном ответе действует увиденный первым (§9).
- [x] Схема SSE + `POST` без подписи, пара задаётся вручную (`protocol/README.md`; токены сторон в `pairs.json`,
      пара — командой `add-pair`).
- [x] Подтверждение доставки — отдельный `POST` получателя (`acks`); неподтверждённое на открытом потоке повторно не
      шлётся, приходит снова при следующем входе, получатель отбрасывает обработанные `id`.
- [x] Порядок доставки по двум путям сервера (§6.2): единый `seq` на пару, один исходящий порядок на поток.
- [x] У стороны один поток: новый вход закрывает прежний. Порог «поток без признаков жизни» (§4) — 45 с, `ping` раз в
      15 с, любой авторизованный `POST` — признак жизни; обрыв TCP сервер видит за доли секунды. Приложение,
      уходя с экрана, ждёт подтверждения своих `POST` до 2 с, затем закрывает поток.
- [x] Закрытие потока при уходе приложения с экрана; как быстро его видят сервер и desktop (F-8). Сигнал о потоке
      телефона идёт после всех принятых от него сообщений, при входе ПК — текущее состояние (§4). Штатный уход (Home,
      гашение экрана): окно текста на ПК отпускается за ~1 с, локально и через Caddy на стенде. Не проверено: заморозка
      процесса до `onStop` (тогда — порог 45 с).
- [ ] На этапе 1 снимка нет: карточки живут в памяти процесса приложения и при его убийстве восстанавливаются только
      из очереди сервера; снимок — этап 3 (§5.2).
- [ ] Свои хуки рядом с хуками AgentGlow в настройках Claude Code: установка и удаление не трогают чужие.
- [x] Сервер на aokaztest.ru за Caddy — путь `/pult/` (без новой записи DNS и сертификата), реле на 127.0.0.1:8082,
      `flush_interval -1`; по правилам стенда stop-фильтр журнала для IP и журналы не дольше 30 дней.
- [x] Порт приёма хуков desktop по умолчанию — 47652 (`hook_port` в `settings.txt`): 47651 занят AgentGlow.

## Этап 2 — ключи, сопряжение, шифрование
Нормативно — `protocol/CRYPTO.md`, векторы — `protocol/vectors/` (D-62…D-70).
- [x] Подпись каждого запроса, вход «вызов — ответ» и привязка к открытому потоку SSE, защита от повтора — окно 128 на
      поток (CRYPTO §4).
- [x] Проверка подписи P-256 на сервере — `python3-cryptography` из apt (D-68).
- [x] minSdk mobile — 31 (D-67, F-3).
- [x] Заверение ключей телефона — HMAC секретом QR над стенограммой; отпечаток — 16 цифр (CRYPTO §3).
- [x] Шифрование: ECDH → HKDF-SHA256, ключ на направление, AES-256-GCM, открытые поля — связанные данные (CRYPTO §5, §6).
- [x] Срок заявки — 600 с, константа протокола; телефон ждёт `hello` 120 с от ответа сервера на свои ключи (D-63).
- [x] Когда поднимается номер версии (D-69).
- [x] Классы срока жизни сообщений — D-85 (`protocol/MESSAGES.md` §1.3); `unpair` и `notification` не используются (D-77),
      сигналы сервера — не конверты. `hello` — 120 с (D-72).
- [x] Карточка «отправлено» на телефоне — по подтверждению приёма сервером; без подтверждения повтор с тем же
      идентификатором конверта, новым `Pult-N` и подписью.
- [x] Server: заявки и состояние пары (`pending` → `active` → удалена с причиной) на диске, вызовы и потоки — в памяти;
      `add-pair` и токены убраны; `cryptography` — зависимость (README сервера: «только стандартная библиотека» больше не
      так); тест проходит `auth.json` целиком и `reject` из `envelope.json`, видимые без ключа.
- [x] Desktop: ключи в CNG, P/Invoke AES-GCM (проверить и под x86, если сборка x86), окно QR с заявкой и её обновлением
      по сроку, проверка `tag`, отпечаток, `hello`; тест проходит `pairing.json` и `envelope.json`, своя подпись — через
      эталонную проверку.
- [x] Mobile: minSdk 31, сканер QR, ключи Keystore, перевод DER → P1363, ожидание `hello`; тест векторов на программных
      ключах JCA и на устройстве — подпись и ECDH ключами Keystore. Токен пары из SharedPreferences уходит вместе с
      этапом 1.
- [x] Удаление ключей пары при разрыве на обеих сторонах.
- [x] Проверка подписанного запроса сервером идёт в таком порядке (CRYPTO §4.3): заголовки есть (`401 unauthorized`) →
      `Pult-Stream` — текущий поток стороны (`401 stale_stream`) → подпись верна (`401 bad_signature` и `intrusion`) → `n`
      в окне повтора (`409 replay`) → только потом разбор тела и конверта (`400 bad_envelope`).
- [x] Нерасшифровавшийся конверт подтверждается и отбрасывается (D-71); приём хуков desktop повторяет привязку порта (D-76).
- [ ] Не проверено вживую на устройстве: ключ согласования в Keystore на старом Keymaster, обновлённом до Android 12
      (`SecurityLevel.SOFTWARE`) — телефон предупреждает, но сопряжение идёт.

## Этап 3 — статусы, лента, снимок, сессия
Нормативно — `protocol/MESSAGES.md`, примеры — `protocol/vectors/messages.json` и эталонная модель `messages.py`
(D-77…D-91). Решено спецификацией:
- [x] Снимок без лент, хвосты — `feed` после него от `feeds` телефона, `seq` записи для стыка (D-79, D-81).
- [x] Переподключение без `Last-Event-ID`, гарантия «ничего не пропало» и её пределы (MESSAGES §7).
- [x] Срок ожидания хука больше N — не бывает: 540 с < 900 с (D-90).
- [x] Срок хранения причины — 7 суток (D-73); порог повторного входа — 60 с и после блокировки, и после сворачивания (D-88).
- [x] Снимок в лимите конверта — части, обязательное первым, хвосты остатком (D-81).
- [x] Гонка `hello` / запрос — одна упорядоченная очередь ПК и атомарный снимок (D-83).
- [x] Правила отрисовки недоверенной ленты (D-89).
- [x] Принятый текст в ленте — запись `user` с `via: "phone"`; неприменённый — черновик (MESSAGES §3.3, §4.5).

Задачи разбиты по блокам; каждую закрывает свой тест плюс общий сквозной прогон в конце. Готовность блока — проходит
`messages.json` своим тестом (тест читает файл, значения не копирует) и критерии задач.
