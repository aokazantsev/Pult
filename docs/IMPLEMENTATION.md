# Детали реализации по этапам

Детали, которые решаются в коде, а не в архитектуре. Этапы — §10 ARCHITECTURE.md.

## Этап 1 — сквозной прототип
- [ ] Локальный канал хука недоступен другим учётным записям Windows; на loopback (D-54) — секрет установки и
      проверка хуком, что порт держит наше фоновое приложение (для HTTP-хука — условие выбора, §2).
- [ ] Где хранится настройка ожидания Pult и как desktop прописывает таймаут хука в настройках агента.
- [ ] Схема SSE + `POST` без подписи, пара задаётся вручную.
- [ ] Подтверждение доставки — отдельный `POST` получателя; что делает сервер, если поток получателя открыт, а
      подтверждения нет.
- [ ] Порядок доставки по двум путям сервера (§6.2): последовательные `POST` с подтверждением приёма либо точка
      отсчёта в снимке.
- [ ] У стороны один поток: новый вход закрывает прежний; куда идут события при полуоткрытом старом потоке. Порог
      «поток без признаков жизни» (§4). Как приложение, уходя с экрана, дожидается подтверждения приёма своих `POST`.
- [ ] Закрытие потока при уходе приложения с экрана; как быстро его видят сервер и desktop (F-8). Сигнал о потоке
      телефона после принятых от него сообщений; текущее состояние при входе ПК (§4).
- [ ] Свои хуки рядом с хуками AgentGlow в настройках Claude Code: установка и удаление не трогают чужие.
- [ ] Сервер на aokaztest.ru за Caddy — путь или поддомен; по правилам стенда stop-фильтр журнала для IP и журналы не
      дольше 30 дней.

## Этап 2 — ключи, сопряжение, шифрование
- [ ] Подпись каждого `POST`, вход «вызов — ответ» и привязка к открытому потоку SSE; защита от повтора.
- [ ] Проверка подписи P-256 на сервере (Python) — библиотекой из пакетов Ubuntu 22.04.
- [ ] minSdk mobile по F-3.
- [ ] Способ заверения ключей телефона для ПК (одноразовый секрет в QR / фиксация до раскрытия), длина отпечатка.
- [ ] Шифрование с аутентификацией открытых полей конверта; разделение направлений (ключи по направлению или
      отправитель в связанных данных), KDF.
- [ ] Срок жизни заявки сопряжения: значение, где задан (в QR или константа протокола), от чего телефон отсчитывает
      ожидание `hello`.
- [ ] Когда поднимается номер версии протокола: новый тип идёт возможностью в `hello` без смены версии, версия
      меняется только при несовместимом изменении конверта.
- [ ] Классы срока жизни служебных сообщений (`resolved`, `unpair`, `hello`, `notification`, сигнал сервера о
      чужой попытке входа) под общим потолком сервера.
- [ ] Карточка «отправлено» на телефоне — по подтверждению приёма сервером; без подтверждения повтор с тем же
      идентификатором.

## Этап 3 — статусы, лента, снимок, сессия
- [ ] Снимок несёт хвост ленты треда, а не всю ленту; размер хвоста; порядковый номер записи ленты в треде для
      поиска стыка.
- [ ] Переподключение потока (`Last-Event-ID` или только снимок; порог и один поток — этап 1) и проверка «после обрыва ничего не пропало».
- [ ] Срок ожидания хука больше N простоя — исход: сессия рвётся раньше, хук отпускает в обычный диалог.
- [ ] Срок хранения причины удаления пары на сервере (D-50); порог повторного входа на телефоне (D-51).
- [ ] Снимок укладывается в лимит размера конверта — хвост ленты и/или части снимка; открытые запросы, исходы
      закрытых, статусы и режим идут обязательно и первыми.
- [ ] Снимок собирается и отправляется в одном упорядоченном потоке с событиями ПК: запрос, созданный во время сборки
      снимка, не попадает «за» снимок и не закрывается им как «неизвестен»; тест на гонку `hello` / запрос.
- [ ] Правила отрисовки недоверенной ленты — подмножество разметки, без загрузки внешних ресурсов, ссылки не
      открываются автоматически.
- [ ] Принятый текст с телефона в ленте — одна реплика (запись транскрипта, карточка ответа её не дублирует);
      отвергнутый или неотправленный текст остаётся у пользователя черновиком.

## Этап 4 — сервер и выпуск
- [ ] Пороги серверных лимитов: заявки и пары с одного адреса, верхняя граница срока жизни конверта.
- [ ] Пороги размера конверта и объёма трафика пары за период.
- [ ] Пары, очередь и причины — на диске; после старта сервер считает «без ПК» (D-26) с момента старта; простой ночной
      перезагрузки стенда вместе с повтором desktop укладывается в 5 минут, иначе — строка в §9.

## Отложено (D-44: пуши и RuStore)
- [ ] Политика стабильности публичного API шлюза: версия в пути, обратная совместимость, предупреждение об
      устаревании.
- [ ] Ограничение частоты пробуждений: на идентификатор и на источник, пороги.
- [ ] Обновление пуш-токена RuStore в шлюзе при его смене провайдером.
- [ ] Каким ключом подписаны регистрация и удаление идентификатора в шлюзе.
- [ ] Срок ожидания подтверждения доставки, после которого сервер будит телефон пушем.
- [ ] После забора сообщений телефон показывает локальное уведомление на каждый открытый запрос, нажатие ведёт в его
      тред.
- [ ] Шлюз сборки не в списке сервера (D-27) — сессия работает без пушей, приложение один раз показывает «сервер не
      будит телефон этой сборки»; повторная регистрация — только при новом сопряжении.
