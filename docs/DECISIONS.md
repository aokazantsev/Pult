| D-64 | Шифрование: ECDH → HKDF-SHA256 (соль — хеш стенограммы сопряжения), отдельный ключ на каждое направление, AES-256-GCM со случайным 96-битным нонсом, открытые поля конверта — связанные данные; получатель отвергает конверт со своим `from` (обе стороны знают оба ключа — иначе сервер отражал бы конверт отправителю). Отдельной подписи конверта (`sig`) нет: подлинность между ПК и телефоном даёт AEAD, перед сервером — подпись запроса над байтами тела. Случайный нонс вместо счётчика — счётчик пришлось бы надёжно хранить при каждом сообщении (07.11.2026, CRYPTO §5, §6) |
| D-65 | Вход: одноразовый вызов сервера → подписанный вход открывает поток → сервер выдаёт идентификатор потока. Каждый запрос к паре подписан над операцией, парой, стороной, потоком, счётчиком и хешем тела; окно повтора — 128 значений счётчика на поток; запрос не с текущим открытым потоком отвергается. Сервер принимает любой выданный им живой вызов, новый не вытесняет прежние: иначе знающий `pair` из QR не давал бы войти. Операция вместо пути — подпись не зависит от префикса прокси (07.11.2026, CRYPTO §4) |
| D-66 | Токены этапа 1, версия протокола 1 и команда `add-pair` сняты; пара появляется только через заявку и QR, пути — `/v2`. Причина: второй способ входа — вторая поверхность атаки, а предыдущая версия в MVP не поддерживается (§6.4 ARCHITECTURE) (07.11.2026) |
| D-67 | Ключи телефона — Android Keystore (уровень проверяется `KeyInfo.securityLevel`; программный — предупреждение, не отказ), без StrongBox и без привязки к биометрии; minSdk 31 (Android 12): согласование ключей в Keystore — с API 31 (F-3). Обход для API 29–30 (программный ключ согласования, завёрнутый ключом Keystore) отвергнут: закрытый ключ попадал бы в память процесса. Ключи ПК — CNG, Microsoft Software Key Storage Provider, неэкспортируемые. Уточняет D-53 (07.11.2026) |
| D-68 | Сервер проверяет подписи пакетом `cryptography` (на стенде — `python3-cryptography` из apt Ubuntu 22.04, 3.4.8, его достаточно); своя арифметика кривой отвергнута. AES и ECDH серверу не нужны (07.11.2026) |
| D-69 | Номер версии протокола меняется только при несовместимом изменении конверта, криптографии, входа или смысла существующих типов; новый тип — возможность в `hello`. Совместимость проверяется по `/info` до сопряжения и при каждом подключении, по версиям в QR и `hello`; порядок полей и смысл `v` конверта не меняются ни в одной версии, чтобы несовместимость распознавалась без расшифровки (07.11.2026, CRYPTO §8) |
| D-70 | Очередь получателя на сервере ограничена и числом сообщений (200, `429 queue_full`), и суммарным размером (4 МиБ, `PULT_MAX_QUEUE_BYTES`, `507 queue_bytes_full`): без предела по байтам 200 конвертов по 64 КБ на каждую пару роняли реле по памяти при каждом старте. Тело `POST` принимается и chunked (HTTP/2 без длины) до того же предела 64 КБ (07.11.2026) |
