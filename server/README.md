# Pult server

Реле между ПК и телефоном, протокол 2: заявка на сопряжение и пары, вход «вызов — ответ», проверка подписи каждого
запроса, поток SSE и `POST` для обеих сторон, очередь на получателя на диске, служебные сигналы, порог живости.
Сообщения (`ct`) сервер не расшифровывает и не может подделать: у него только открытые ключи. Нормативно — [`protocol/CRYPTO.md`](../protocol/CRYPTO.md)
и [`protocol/README.md`](../protocol/README.md). Python 3.10+, пакет `cryptography` (на стенде — `python3-cryptography`
из apt Ubuntu 22.04, 3.4.8; больше ничего).

## Запуск

```bash
python3 -m pip install --user cryptography
python3 -m pult_relay run
```

Windows — `run.cmd`, Linux — `run.sh`. Токенов и `add-pair` нет: пара появляется только через заявку ПК и QR
(`POST /v2/claims`), поэтому сервер стартует пустым и печатает только адрес и каталог данных.

| Переменная | По умолчанию | |
|---|---|---|

| `PULT_HOST`, `PULT_PORT` | `127.0.0.1`, `8082` | адрес; на Windows порт занимается исключительно (второй процесс на нём не сядет), на Linux — `SO_REUSEADDR` |
| `PULT_TRUST_PROXY` | выкл | `1` — адрес клиента для частоты и пределов на адрес берётся из последнего значения `X-Forwarded-For` (за Caddy/nginx) |
| `PULT_CLAIM_TTL` | `600` | срок заявки без скана, с |
| `PULT_PC_OFFLINE` | `300` | ПК без связи дольше этого — пара удаляется, причина `pc_offline` (D-26) |
| `PULT_DELETED_KEEP` | `604800` | срок хранения причины удаления и открытых ключей, с (7 суток) |
| `PULT_MAX_PENDING` | `200` | заявок без скана одновременно (дальше `429 rate_limited`) |
| `PULT_MAX_PAIRS_PER_ADDR` | `6` | заявок и активных пар одного адреса — адреса заявки ПК, после перезапуска — адреса первого входа ПК или первой записи в очередь (в памяти процесса; дальше `429 rate_limited`) |

| `PULT_RATE_WRITES` | `120` | записей очереди в минуту с одного адреса: конверты с `ttl > 0` и `acks`, которые что-то удалили (дальше `429 rate_limited`) |
| `PULT_MAX_TTL` | `900` | верхняя граница срока жизни конверта в очереди, с |
| `PULT_MAX_QUEUE` | `200` | очередь на получателя, сообщений |
| `PULT_MAX_QUEUE_BYTES` | `4194304` | очередь на получателя, суммарный размер конвертов, байт |
| `PULT_MAX_TOTAL_QUEUE_BYTES` | `33554432` | очереди всех пар вместе, байт, 1 КиБ на сообщение сверху; пар одного адреса — треть; пара без известного адреса (после перезапуска) получает адрес того, кто первым положил конверт в её очередь (дальше `507 queue_bytes_full`) |
| `PULT_MAX_ENVELOPE` | `65536` | размер тела подписанного запроса, байт |
| `PULT_KEEPALIVE`, `PULT_LIVENESS` | `15`, `45` | комментарий в потоке; порог «без признаков жизни», с |

## Что делает сервер

- **Заявка и пара.** `POST /v2/claims` выдаёт `pair` (16 случайных байт) и держит пару в `pending` 600 с. Первая заявка
  телефона `POST /v2/claims/{pair}`, правильная по форме, сжигает заявку и переводит пару в `active`; неверная по форме —
  `400 bad_key`/`bad_tag`, заявка цела. Второй скан — `409 claim_used` и сигнал `intrusion`. Заверение (`tag`) сервер не
  проверяет: у него нет секрета QR, проверяет ПК.
- **Вызов и вход.** `POST …/challenge` выдаёт `base64url(срок ‖ случайное ‖ HMAC)` без хранения выданных; хранится
  только множество предъявленных до их срока. Новый вызов прежние не вытесняет. `GET …/stream` с подписью открывает
  поток и выдаёт `stream`; вызов сгорает при любой попытке.
- **Подписанные запросы.** `messages`, `acks`, `ping`, `delete`, `state`: поток текущий (`stale_stream`), подпись верна
  (`bad_signature` + `intrusion`), счётчик `n` в окне 128 на поток (`replay`). Подпись проверяется до разбора тела.
- **Конверт v2.** Ровно семь полей, `ct` канонический base64url не короче нонса и тега; `ttl` обрезается только для
  очереди, получателю уходит исходный конверт. Чужая версия — `400 unsupported_version` и сигнал `phone_incompatible`
  ПК, если отправитель — телефон. Конверт доставляется только противоположной стороне: `from` в конверте обязан
  совпасть с `Pult-From`, так что стороне свой конверт сервер не возвращает.
- **Очередь.** Как на этапе 1: `ttl = 0` — мимо очереди; `ttl > 0` — на диске до `acks` или срока; повторный `id` — `dup`;
  один `seq` на пару; `429 queue_full`, `507 queue_bytes_full`, `411`, `413`, chunked.
- **Сигналы.** `session`, `pair` (при каждом входе ПК в `active` пару), `phone_stream` (при входе ПК — после очереди от телефона),
  `intrusion` и `phone_incompatible` (не чаще раза в минуту на пару), `pair_deleted`.
- **Поток, который не успевает читать.** Неотправленные сообщения считаются по длине `ct` плюс 1 КиБ на сообщение: на поток —
  не больше `PULT_MAX_QUEUE_BYTES` плюс 1 МиБ, на потоки одного адреса — половина `PULT_MAX_TOTAL_QUEUE_BYTES`, на все — весь
  `PULT_MAX_TOTAL_QUEUE_BYTES`. Сверх — поток закрывается; очередь, которая не уместилась при входе, — поток закрывается после
  уже отданного по порядку. Служебный сигнал потоку, у которого не отправлено 1000 элементов и больше, тоже закрывает
  поток. Неподтверждённое из очереди придёт при следующем входе, `ttl = 0` теряется.
- **Удаление.** Причина и открытые ключи хранятся `PULT_DELETED_KEEP`; вход с верной подписью — `410 pair_deleted` с
  `reason` и `by`. Заявка без скана исчезает без причины. ПК без связи 5 минут — удаление с `pc_offline`.

Состояние (`state.json`: пары, ключи, очереди, память `id`) пишется атомарно при каждом изменении и переживает перезапуск;
приём конверта с `ttl = 0` файл не пишет — его `id` и `seq` попадают на диск со следующей записью.
Не живут между запусками: потоки и их `stream`, вызовы (ключ вызовов — на процесс), счётчики частоты. После перезапуска
клиенты входят заново: старый `stream` — `401 stale_stream`. Файл старого формата (этап 1) переименовывается в
`state.json.old`, битый — в `state.json.corrupt`; `pairs.json` этапа 1 не читается и его можно удалить.

## Ограничения

Пределы защищают память и потоки процесса от одного адреса и от своей пары: реле не падает и после перезапуска
поднимается. Адрес — публичный IP клиента (за прокси — из `X-Forwarded-For` при `PULT_TRUST_PROXY`): клиенты за общим
NAT делят его пределы. Адреса пар живут в памяти: после перезапуска пара снова входит в пределы адреса с первым входом ПК или первой записью в её очередь.
До этого (не дольше `PULT_PC_OFFLINE` после старта) нетронутые очереди прежних пар адреса не входят в его треть: вместе с
новыми он держит до двух третей общего предела, треть остаётся остальным.
Отказ в обслуживании пределы не исключают: клиент с нескольких адресов занимает `PULT_MAX_CONNECTIONS`, а
очереди своих пар до `PULT_MAX_TOTAL_QUEUE_BYTES` — тогда конверты с `ttl > 0` всех пар получают `507`, пока его
конверты не истекут (до `PULT_MAX_TTL`).
Если соединения заняты так долго, что ПК не входит дольше `PULT_PC_OFFLINE`, его пара удаляется с `pc_offline` — в том
числе когда на связи больше пар, чем вмещает `PULT_MAX_CONNECTIONS`. Потоки
нескольких адресов, которые читают медленно, занимают общий бюджет неотправленного — тогда потоки остальных пар
закрываются на очередном сообщении. Каждое изменение очереди переписывает `state.json` целиком под общим замком: пара,
которая шлёт и подтверждает конверты с `ttl > 0` при полной очереди, замедляет ответы всех пар (с одного адреса — не чаще
`PULT_RATE_WRITES` таких записей в минуту), но не останавливает реле.
Не записался `state.json` (диск полон, нет прав) — запрос получает `500 internal`, в журнал уходит traceback; конверт или
сигнал сопряжения, который этот запрос отдаёт открытому потоку, уже отдан. Изменение остаётся в памяти и попадает на диск
со следующей удачной записью, а перезапуск до неё его теряет.

## Тесты

```bash
python3 -m unittest discover -s tests -t .
```

Все векторы `protocol/vectors/*.json` (подписи, окно повтора, отрицательные конверты), сценарии сопряжения, повтора, чужой
подписи, просроченного вызова, перезапуска процесса (очередь и пары целы), тестовый клиент на векторах ключей.

## Тестовый клиент

`tools/pult_testclient.py` — библиотека обеих сторон (ключи, QR, заверение, ключи пары, конверт, вход, подпись запросов,
`stale_stream` с повторным входом); `tools/pult_cli.py` — командная строка. Запуск из каталога `server/`, сервер —
`python3 -m pult_relay run` (по умолчанию `http://127.0.0.1:8082`; другой — `--server` до подкоманды:
`python3 -m tools.pult_cli --server https://aokaztest.ru/pult demo`).

```bash
python3 -m tools.pult_cli demo
```

Сквозной сценарий в одном процессе: заявка, QR, скан, проверка `tag`, `hello`, запрос разрешения и ответ, удаление.

Настоящий desktop против тестового телефона, или настоящий телефон против тестового ПК — по одной стороне:

```bash
python3 -m tools.pult_cli --server https://aokaztest.ru/pult pc --state pc.json --qr-file qr.json --auto
python3 -m tools.pult_cli phone --state phone.json --qr-file qr.json --auto
```

- `pc` создаёт заявку, печатает QR (JSON из CRYPTO §3.2; для настоящего телефона — превратить в картинку любым генератором QR),
  ждёт скана, проверяет `tag`, шлёт `hello` и слушает. Адрес `--server` попадает в QR: для настоящего телефона — https-адрес
  реле, доступный с телефона (релизная сборка `http://` не принимает). `phone --qr '<json>'` или `--qr-file` сканирует (адрес
  берёт из QR, `--server` не читает), ждёт `hello` ПК и слушает.
- `--auto` отвечает сам: `allow` на `permission_request`, первый вариант на `choice_request`, `ok` на `text_request`.
- Строка из стандартного ввода, начинающаяся с `{`, отправляется сообщением (`{"type":"permission_request",…}`),
  принятое печатается расшифрованным. `--state` сохраняет ключи после сопряжения: повторный запуск входит в ту же пару.
  `--seconds N` — слушать N секунд и выйти; `--idle` — срок простоя в QR.
