# Pult, протокол 2: ключи, сопряжение, шифрование, подпись

Нормативная спецификация этапа 2. Реализации server, desktop и mobile делаются строго по ней и обязаны пройти
эталонные векторы [`vectors/`](vectors/) своим тестом (§10). Архитектура — [`docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md)
§3–§6, решения — D-62…D-70 в [`docs/DECISIONS.md`](../docs/DECISIONS.md). Запросы, поток SSE и типы сообщений —
[`README.md`](README.md).

Слова «обязан», «нельзя» — требования; расхождение реализации с векторами — ошибка реализации.

## 1. Кодирование

| Что | Формат |
|---|---|
| Двоичное в JSON, заголовках, QR | base64url без `=` (RFC 4648 §5), каноническое: неиспользуемые биты последнего символа — нули. Неканоническое, с `=`, с `+` `/` — отвергается. Декодеры из коробки этого не проверяют (Java `Base64.getUrlDecoder()` пропускает ненулевые биты, Python без `validate` выбрасывает чужие символы, в .NET 4.8 base64url нет): проверять как эталон `b64u_decode` — алфавит `[A-Za-z0-9_-]`, длина не `4k+1`, затем декодировать и сравнить повторное кодирование со входом |
| Открытый ключ P-256 | точка SEC1 без сжатия: `0x04 ‖ X ‖ Y`, 65 байт, X и Y — 32 байта big-endian с ведущими нулями. В base64url — 87 символов |
| Подпись | ECDSA P-256 над SHA-256, формат IEEE P1363: `r ‖ s`, по 32 байта big-endian, 64 байта. В base64url — 86 символов. DER не принимается |
| Строка для подписи, HMAC, AAD | строки, соединённые `\n` (0x0A), в UTF-8, без завершающего `\n` |
| Идентификаторы (`pair`, `id`, `stream`, `challenge`) | только `[A-Za-z0-9_-]`, 1–64 символа: разделитель `\n` в них невозможен |
| Числа (`v`, `ts`, `ttl`) | целое JSON от 0 до 2^53−1; в строке для подписи и AAD — десятичное без ведущих нулей и знака. `600.0`, `2.0`, `true`, строка, `NaN` — отвергаются |
| Заголовок `Pult-N` | `[1-9][0-9]*`, значение от 1 до 2^53−1, иначе `400 bad_header`; в строку для подписи идёт текст заголовка как есть — он и есть каноническая запись |
| JSON | UTF-8; повторный ключ в любом объекте (конверт, QR, тела запросов, сигналы) — отвергается: парсеры по-разному берут первое или последнее значение. В Python — `object_pairs_hook`, в Kotlin и .NET — проверка при разборе |
| Случайные байты | только криптостойкий генератор: `SecureRandom`, `RandomNumberGenerator`, `secrets` |

Проверка подписи принимает обе формы `s` (low-S и high-S): Android Keystore и CNG не нормализуют `s`. Поэтому подпись
не годится как идентификатор и нигде им не служит. `r` и `s` вне `[1, n−1]` — подпись неверна.

## 2. Ключи

| Сторона | Ключ | Назначение | Где лежит закрытый |
|---|---|---|---|
| ПК | `pc_sign` | ECDSA: вход и запросы к серверу | CNG, Microsoft Software Key Storage Provider, профиль пользователя, `ExportPolicy = None` |
| ПК | `pc_agree` | ECDH: общий ключ пары | там же |
| Телефон | `phone_sign` | ECDSA: вход и запросы к серверу | Android Keystore, `PURPOSE_SIGN`, `DIGEST_SHA256` |
| Телефон | `phone_agree` | ECDH: общий ключ пары | Android Keystore, `PURPOSE_AGREE_KEY` (API 31) |

- Все четыре — P-256 (`secp256r1`). Новая пара ключей на каждое сопряжение; при разрыве (§5.4 ARCHITECTURE) сторона
  удаляет свои ключи пары (CNG — `CngKey.Delete`, Keystore — `deleteEntry`).
- Телефон проверяет `KeyInfo.securityLevel` обоих ключей. На части устройств, обновлённых до Android 12 со старым
  Keymaster, ключ согласования может исполняться программно (`SOFTWARE`), а не в TEE: сопряжение идёт, но телефон один
  раз показывает «ключи не в аппаратном хранилище» и пишет это в журнал (§9).
- StrongBox не используется: согласование ключей в нём не обязательно. Привязки ключа к биометрии нет: вход в
  приложение защищает экран (D-19, D-51), а ключи нужны потоку сразу при возврате на экран.
- Сервер хранит только открытые ключи четырёх видов. Подписи проверяет только сервер; ПК и телефон подписей друг друга
  не проверяют: подлинность сообщений между ними даёт AEAD (§6).
- Секрет заявки `K` и выведенные ключи пары живут только в памяти процесса; `K` стирается после сопряжения. Ключи
  направления пересчитываются при каждом старте из своего закрытого ключа и **сохранённых** открытых ключей пары.
- Открытые ключи собеседника и `pair` каждая сторона сохраняет у себя в момент сопряжения (телефон — из QR, ПК — после
  проверки `tag`, §3.4) и дальше берёт только оттуда. Ключи, пришедшие от сервера после сопряжения, ничего не меняют.

## 3. Сопряжение

### 3.1. Заявка ПК

1. ПК проверяет `GET /info` (§8) и создаёт `pc_sign`, `pc_agree`, секрет `K` — 32 случайных байта.
2. `POST /v2/claims`, без подписи (защищает ограничение частоты по адресу):
   ```json
   {"pc_sign": "<87>", "pc_agree": "<87>"}
   ```
   Ответ `201 {"pair": "<22>", "ttl": 600}`. `pair` — 16 случайных байт сервера в base64url, это и идентификатор
   заявки, и идентификатор будущей пары. Сервер проверяет, что оба ключа — канонические точки на кривой (`400 bad_key`).
3. Пара на сервере — в состоянии `pending`. ПК входит в неё как обычно (§4) и держит поток: о скане он узнаёт
   служебным сигналом. Сообщения в `pending` не принимаются (`409 not_paired`), удаление — да (ПК закрыл QR).
4. Заявку без скана сервер удаляет через `ttl` = 600 с после создания, без хранения причины. ПК к этому сроку убирает
   QR и, если окно сопряжения открыто, создаёт новую заявку с новыми ключами и новым `K`, старые ключи удаляет.

### 3.2. QR

Содержимое — JSON в UTF-8, без пробелов, порядок ключей — как ниже (пример — `vectors/pairing.json`, поле `qr`):

```json
{"v":[2],"s":"https://example.com/pult","c":"<pair>","k":"<K>","ps":"<pc_sign>","pa":"<pc_agree>","n":14400}
```

| Ключ | Что |
|---|---|
| `v` | версии протокола, которые поддерживает ПК (§8) |
| `s` | базовый адрес сервера, без `/` в конце; к нему дописываются пути (`/info`, `/v2/...`). `https://` обязателен; `http://` телефон принимает только в отладочной сборке |
| `c` | `pair` из ответа сервера |
| `k` | секрет `K`, 32 байта. На сервер не уходит никогда |
| `ps`, `pa` | открытые ключи ПК |
| `n` | срок простоя N в секундах, от 900 до 129600 (D-22) |

Папки сессии в QR не входят: членство решает ПК (D-57). Телефон читает QR только своим сканером и отвергает QR с
лишними или недостающими ключами, неверными типами или неканоническими значениями. QR — не URL: системная камера и
чужие сканеры не открывают его как ссылку.

### 3.3. Ключи телефона и заверение

1. Телефон проверяет `v` QR и `GET /info` сервера (§8), создаёт `phone_sign`, `phone_agree` и строит
   **стенограмму** `T`:
   ```
   T = pair \n pc_sign \n pc_agree \n phone_sign \n phone_agree
   ```
   (ключи — строками base64url, как в QR и на сервере).
2. Заверение: `tag = HMAC-SHA256(K, "pult-v2-claim\n" ‖ T)`, 32 байта.
3. `POST /v2/claims/{pair}`, без подписи:
   ```json
   {"phone_sign": "<87>", "phone_agree": "<87>", "tag": "<43>"}
   ```
   Ответ `200 {"pair": "<pair>"}`. Исходы по порядку проверки:
   - неизвестная или истёкшая заявка — `404 not_found`;
   - уже сожжённая — `409 claim_used` (телефон показывает «QR уже использован, нужен новый на ПК»), ПК получает
     сигнал `intrusion` (§7);
   - тело не по форме (лишние или повторные ключи, ключ не каноническая точка на кривой, `tag` не 32 байта в
     каноническом base64url) — `400 bad_key` или `400 bad_tag`, заявку **не** сжигает: сервер проверяет только форму;
   - иначе заявка **сжигается** (D-14, D-25), верен `tag` или нет — сервер этого знать не может.
4. Сервер переводит пару в `active` и шлёт ПК сигнал `pair` с ключами телефона и `tag`; ПК, не получивший его вживую,
   получает его при каждом входе в `active` пару (§7).
5. Телефон сразу входит (§4), открывает поток и ждёт сообщение `hello` от ПК (`from = pc`, §6) **120 с** по своим часам с момента
   ответа `200`. Расшифровался `hello` — сопряжение закончено, пара активна. Не дождался — `delete` с причиной
   `no_hello` (§4.4) и «сопряжение не завершено, отсканируйте новый QR».

### 3.4. Проверка на ПК

ПК по сигналу `pair` строит `T` из своих ключей и полученных ключей телефона и сравнивает `tag` за постоянное время
(в .NET 4.8 готовой функции нет — свой цикл с OR по байтам).

- **Сошлось** — сессия за тем, кто отсканировал первым: ПК сохраняет ключи телефона (§2), QR исчезает, ПК выводит
  ключи пары (§5), шлёт `hello` (затем снимок, этап 3). `K` стирается. Последующие сигналы `pair` ПК только сравнивает
  с сохранёнными: расхождение — та же фраза, что у `intrusion`, ключи не меняются.
- **Не сошлось** (сервер подменил ключи телефона или сканировал не держатель QR) — `delete` с причиной
  `pairing_rejected`, ключи стираются, ПК показывает «попытка сопряжения не прошла проверку» и предлагает новый QR
  (D-14).
- **ПК перезапустился, пока заявка ждёт скана** — `K` потерян: заявка удаляется (`delete`, причина `user`), нужен
  новый QR. Сигнал `pair` к паре без сохранённых ключей телефона и без `K` в памяти — то же.

### 3.5. Отпечаток

Дополнительная сверка глазами (D-13): `F = SHA-256("pult-v2-fingerprint\n" ‖ T)`, первые 8 байт как беззнаковое
big-endian, по модулю 10^16, 16 цифр с ведущими нулями, показ — четыре группы по четыре: `0652 9522 5708 8854`.
Телефон показывает его сразу после создания ключей, ПК — после проверки `tag`. Отпечаток защищает от утечки QR вместе со
сговором сервера (§9): подогнать свои ключи под отпечаток телефона серверу нужно около 2^53 попыток, пока заявка ждёт.
Без сверки сопряжение всё равно проходит.

## 4. Вход и подпись запросов

### 4.1. Вызов

`POST /v2/pairs/{pair}/challenge`, без подписи, тело `{"from": "pc" | "phone"}` → `200 {"challenge": "<43>", "ttl": 60}`.
`challenge` — непрозрачная для клиента строка сервера (`[A-Za-z0-9_-]{1,64}`), одноразовая, живёт 60 с, привязана к
паре и стороне. Сервер принимает **любой** выданный им, не истёкший и не предъявленный вызов этой пары и стороны:
выдача нового вызова прежние не вытесняет, а сгорает только предъявленный. Иначе любой, кто видел `pair` (он в QR),
запросами вызовов не давал бы войти законной стороне. Удобный способ без хранения выданных вызовов:
`base64url(срок ‖ 16 случайных байт ‖ HMAC-SHA256(ключ сервера, pair ‖ from ‖ срок ‖ случайное)[:16])` плюс множество
предъявленных до их срока; выдача вызовов ограничена по частоте на адрес (`429 rate_limited`). Пары нет, или у неё ещё нет ключей этой стороны (`phone` в `pending`) — `404 not_found`.
Удалённая пара, причина которой ещё хранится, вызов выдаёт — причину сторона получит после подписи (§4.4).

### 4.2. Поток

```
GET /v2/pairs/{pair}/stream
Pult-From: pc
Pult-Challenge: <challenge>
Pult-Sig: <подпись>
```

Подписывается `"pult-v2-login\n" ‖ pair ‖ "\n" ‖ from ‖ "\n" ‖ challenge` ключом `pc_sign` или `phone_sign`. Сервер
сжигает предъявленный вызов при любой попытке, верной или нет. Неверная подпись или неизвестный вызов — `401 bad_signature` и сигнал
`intrusion` сторонам пары (§7). Удалённая пара — `410` (§4.4).

Успех — поток SSE; первое событие потока:

```
event: server
data: {"type":"session","stream":"<22>"}
```

`stream` — 16 случайных байт сервера, идентификатор этого потока. До него клиент запросов к паре не шлёт. Новый вход
стороны закрывает прежний поток и делает его `stream` недействительным.

### 4.3. Подпись запроса

Каждый запрос к паре, кроме §4.1 и §4.2, несёт заголовки:

```
Pult-From: phone
Pult-Stream: <stream>
Pult-N: 7
Pult-Sig: <подпись>
```

Подписывается:

```
"pult-v2-post" \n op \n pair \n from \n stream \n n \n base64url(SHA-256(тело))
```

| `op` | Запрос |
|---|---|
| `messages` | `POST /v2/pairs/{pair}/messages`, тело — конверт (§6) |
| `acks` | `POST /v2/pairs/{pair}/acks` |
| `ping` | `POST /v2/pairs/{pair}/ping`, тело пустое: хеш пустой строки |
| `delete` | `POST /v2/pairs/{pair}/delete` (§4.4) |
| `state` | `GET /v2/pairs/{pair}/state`, тело пустое |

Хешируются ровно байты тела, как их отправил клиент (у chunked — после снятия разбивки на куски). `op` вместо пути — чтобы подпись не зависела от префикса, под
которым сервер стоит за прокси (`/pult` на стенде).

Сервер принимает запрос, только если:
1. `Pult-Stream` — текущий открытый поток стороны `Pult-From` этой пары, иначе `401 stale_stream`: клиент входит
   заново и повторяет запрос с новым `stream` и новой подписью (конверт тот же, с тем же `id`);
2. подпись верна ключом стороны, иначе `401 bad_signature` и сигнал `intrusion`;
3. `n` проходит окно повтора, иначе `409 replay`;
4. у `messages` в конверте `pair` и `from` совпадают с путём и `Pult-From`, иначе `400 bad_envelope`.

Нет заголовков — `401 unauthorized`. Проверка подписи идёт до разбора тела.

**Окно повтора.** `n` — счётчик клиента на поток: первый запрос — 1, каждый следующий на 1 больше, повтор после ошибки
сети — со следующим `n` и новой подписью. Сервер держит на поток максимум `top` и множество принятых `n` из окна 128:
`n > top` — принять, `top = n`; `n ≤ top − 128` или `n` уже принят — `replay`; иначе принять. Запросы могут идти
параллельно и приходить не по порядку в пределах окна. Состояние окна живёт, пока живёт поток; новый поток — новый
`stream`, поэтому подписанный запрос одного потока не годится ни для другого потока, ни для другой пары.
Последовательность для теста — `vectors/auth.json`, `replay_window`.

### 4.4. Удаление пары

`POST /v2/pairs/{pair}/delete`, подписан (`op = delete`), тело `{"reason": "<причина>"}`:

| `reason` | Кто | Когда |
|---|---|---|
| `user` | ПК или телефон | «Разорвать» на ПК, отвязка на телефоне |
| `idle` | ПК | простой N |
| `replaced` | сторона нового сопряжения | новое сопряжение рвёт прежнюю сессию этой стороны |
| `pairing_rejected` | ПК | `tag` не сошёлся (§3.4) |
| `no_hello` | телефон | нет `hello` за 120 с (§3.3) |
| `pc_offline` | сервер сам | ПК без связи дольше 5 минут (D-26) |

Другое значение — `400 bad_reason`. Сервер шлёт в открытые потоки обеих сторон `{"type":"pair_deleted","reason","by"}`,
закрывает их и хранит причину вместе с открытыми ключами ограниченный срок (D-50; срок — этап 3). Вход в удалённую пару
с верной подписью получает `410 {"error":"pair_deleted","reason":"<reason>","by":"pc"|"phone"|"server"}`; после срока
хранения — `404 not_found`. Неверная подпись причину не получает.
Подписанный запрос к удалённой паре со старым `stream` получает `401 stale_stream`, как при смене потока: сторона входит заново и узнаёт причину.

## 5. Ключи пары

```
Z     = ECDH(свой agree, чужой agree)          32 байта, координата X общей точки
salt  = SHA-256("pult-v2-salt\n" ‖ T)
PRK   = HMAC-SHA256(salt, Z)                    HKDF-Extract
K_pc    = HMAC-SHA256(PRK, "pult-v2-key-pc-phone" ‖ 0x01)   HKDF-Expand, L = 32
K_phone = HMAC-SHA256(PRK, "pult-v2-key-phone-pc" ‖ 0x01)
```

`K_pc` шифрует конверты `from = pc`, `K_phone` — `from = phone`. Обе стороны знают оба ключа, поэтому разделение
направлений держится на проверке получателя: конверт с `from`, равным своей стороне, отвергается до расшифровки (§6).
Без неё сервер вернул бы стороне её же конверт — например, `hello` телефона телефону во время сопряжения (§3.3 п. 5).
Обе стороны вычисляют оба ключа; совпадение с векторами обязательно на каждой
платформе (`vectors/pairing.json`). `T` входит в соль, поэтому ключи привязаны к паре и ко всем четырём открытым ключам.

## 6. Конверт

```json
{"v":2,"pair":"<pair>","from":"pc","id":"pc-0001","ts":1793989146,"ttl":600,"ct":"<base64url>"}
```

Ровно эти семь полей: лишнее (в том числе `inner` и `sig`) или недостающее — конверт отвергается и сервером
(`400 bad_envelope`), и получателем. `id` — `[A-Za-z0-9_-]{1,64}`, уникален на сессию. `ts` — время отправителя
в секундах, никто не сверяет.

**Шифрование** — AES-256-GCM, тег 16 байт:

```
nonce = 12 случайных байт, новый на каждый конверт
AAD   = "pult-v2-env" \n v \n pair \n from \n id \n ts \n ttl
ct    = base64url(nonce ‖ шифртекст ‖ тег)
```

Открытый текст — объект `{"type": ..., ...}` (типы — [`README.md`](README.md)) в JSON, UTF-8. Случайный нонс выбран
вместо счётчика: счётчик пришлось бы надёжно хранить на диске при каждом сообщении, а перезапуск desktop или
приложения с потерей счётчика повторил бы нонс; при числе сообщений сессии на много порядков меньше 2^32 риск
совпадения случайных нонсов пренебрежим.

**Подписи у конверта нет.** Подлинность и целостность между ПК и телефоном даёт AEAD: ключ направления есть только у
них. Перед сервером запрос подписан целиком (§4.3), подпись покрывает байты конверта. Вторая подпись ничего не
добавляла бы, а получателю пришлось бы проверять ECDSA.

**Получатель:** проверяет поля (как сервер), `pair` — своя пара, `from` — сторона собеседника (свой `from` —
отвергнуть), берёт ключ направления по `from`, расшифровывает с AAD. Ошибка — конверт отбрасывается и **подтверждается** (`acks` с его `id`, если `id` — допустимый идентификатор): иначе сервер
слал бы его при каждом входе до `ttl`. Отброшенный конверт получатель записывает в журнал (причина, `id`) и считает в
сводной карточке (§6.1 ARCHITECTURE); пара не рвётся. Не подтверждается только конверт без допустимого `id`: сервер такой
не принимает. Конверт с неподдерживаемым `v` подтверждается так же, после показа несовместимости (§8).
Повтор `id` подтверждается и не применяется (память обработанных — как на этапе 1).

**Сервер:** проверяет поля и пересылает открытые поля без изменений: `ttl` он обрезает только для своей очереди, в
конверте получателю — исходное значение, иначе AAD не сойдётся. Перекодировать JSON сервер может, менять значения —
нет.

Отрицательные случаи (подмена `ttl`, `ts`, `id`, `from`, `pair`, бит шифртекста, свой конверт, отражённый
отправителю, `inner`, лишнее поле, `600.0`, `2.0`, `v: 1`, неканонический base64url, перевод строки в `id`) —
`vectors/envelope.json`, `reject` (объекты, у каждого `to` — кто получатель); повторные ключи и `NaN` — `reject_text`
(сырой текст JSON: разбирать своим строгим парсером). Каждый получатель обязан отвергнуть все; сервер — помеченные
`"server": true`, видимые без ключа.

## 7. Служебные сигналы сервера (этап 2)

`event: server` в потоке; поля открыты серверу.

| `type` | Кому | Поля | Когда |
|---|---|---|---|
| `session` | обоим | `stream` | первое событие каждого потока (§4.2) |
| `pair` | ПК | `phone_sign`, `phone_agree`, `tag` | скан QR; повторяется при каждом входе ПК в `active` пару — ПК, уже проверивший ключи, сравнивает и игнорирует |
| `phone_stream` | ПК | `state` | как на этапе 1 |
| `phone_incompatible` | ПК | `v` | сервер отверг конверт телефона по версии (§8) |
| `intrusion` | обоим | — | неверная подпись входа или запроса, повторный скан QR; не чаще раза в минуту на пару |
| `pair_deleted` | обоим | `reason`, `by` | пара удалена (§4.4), затем поток закрывается |

`intrusion` клиент показывает фиксированной фразой с пометкой «от сервера» (D-39), пару не рвёт (D-15).

## 8. Версии

- Номер версии протокола — целое; этот документ — версия **2**. Версия 1 (этап 1, токены) не поддерживается ни
  сервером, ни клиентами (§6.4 ARCHITECTURE).
- Версия меняется только при несовместимом изменении конверта, криптографии, входа или смысла существующих типов.
  Новый тип сообщения — возможность в `hello` без смены версии (§6.3 ARCHITECTURE).
- `GET /info` → `{"name":"pult-relay","protocol":[2]}` — версии, которые принимает сервер. Пути `/v2/...` — та же
  версия.
- **До сопряжения:** ПК — `/info` перед заявкой; телефон — `v` из QR и `/info` перед отправкой ключей. Общей
  версии нет — отказ с текстом «сервер несовместим» или «версия ПК несовместима» и подсказкой, кого обновить (у кого
  наибольшая версия меньше).
- **При каждом подключении:** `/info` перед входом; несовместим — поток не открывается, человек видит причину.
- **`hello`** (ПК и телефон, при каждом подключении): `{"type":"hello","protocol":[2],"capabilities":[...]}`. Конверт `hello`
  идёт с `ttl` = **120 с** на обеих сторонах: он лежит в очереди сервера, пока собеседник не войдёт и не подтвердит, но не
  дольше окна ожидания `hello` при сопряжении (§3.3 п. 5); устаревший `hello` при следующем подключении заменяется новым.
  Общей версии в `hello` нет — сторона показывает несовместимость, ПК считает версии несовместимыми (запросы сразу в
  обычный диалог, §5.3 п. 2 ARCHITECTURE).
- **Конверт с чужой версией:** сервер отвечает `400 unsupported_version {"protocol":[2]}`; если отправитель — телефон,
  шлёт ПК `phone_incompatible` (D-42). Получатель, увидевший неподдерживаемый `v`, не расшифровывает и показывает
  несовместимость. Порядок полей и смысл `v` в конверте не меняются ни в одной версии — по ним несовместимость
  распознаётся.

## 9. Модель угроз

| Кто | Может | Не может |
|---|---|---|
| Сервер (в том числе чужой, самостоятельный) | видеть открытые поля, размеры и время; не доставить, задержать, переставить, повторить конверт; отказать в сопряжении | прочитать или подделать содержимое; подменить ключи телефона (нет `K`) или ПК (телефон берёт их из QR), в том числе позже — сигналом `pair` (§3.4); вернуть стороне её же конверт (§5); выдать себя за сторону |
| Сеть | то же, что сервер, если нет TLS | при TLS — ничего сверх отказа; без TLS подпись и AEAD держат подлинность и тайну |
| Видевший QR | отсканировать первым и забрать сессию (D-25); знать `pair` и бить по нему неверными входами — стороны видят `intrusion` не чаще раза в минуту | незаметно вклиниться в чужое сопряжение: первый скан сжигает заявку; запросами вызовов не дать войти законной стороне (§4.1) |
| Видевший QR + сервер | подменить ключи телефона с верным `tag` | подогнать 16-значный отпечаток (§3.5) за время заявки: около 2^53 попыток |

Повтор конверта ловит память `id` получателя; перестановку конвертов сервером протокол не ловит — сервер и так
определяет порядок доставки (принятое ограничение). Утечка закрытого ключа раскрывает одну сессию (§9 ARCHITECTURE).
На телефоне, где Keystore исполняет ключ согласования программно (§2), закрытый ключ защищён слабее: его достанет тот,
кто получил права системы на телефоне; сессия от этого не перестаёт работать, человек предупреждён.

## 10. Платформы

### Server — Python 3.10+, пакет `cryptography`

Сервер только проверяет подписи и формат ключей: `ec.EllipticCurvePublicKey.from_encoded_point(ec.SECP256R1(), raw)`,
`utils.encode_dss_signature(r, s)` для перевода P1363 в DER, `public_key.verify(der, data, ec.ECDSA(hashes.SHA256()))`.
Хватает `python3-cryptography` из apt Ubuntu 22.04 (3.4.8). AES и ECDH серверу не нужны.

### Desktop — .NET Framework 4.8, CNG

Проверено на векторах (7.11.2026, csc 4.8, x64):

- Ключи: `CngKey.Create(CngAlgorithm.ECDsaP256 | CngAlgorithm.ECDiffieHellmanP256, имя, new CngKeyCreationParameters { ExportPolicy = None, Provider = MicrosoftSoftwareKeyStorageProvider })`.
  Открытый — `CngKey.Export(CngKeyBlobFormat.EccPublicBlob)`: 8 байт заголовка (`magic`, `cbKey = 32`, little-endian),
  затем X и Y; в SEC1 — `0x04 ‖ X ‖ Y`. Ключ телефона в CNG — тот же блоб с `magic` `0x314B4345` (`ECK1`, ECDH P-256
  public) через `ECDiffieHellmanCngPublicKey.FromByteArray(blob, EccPublicBlob)`.
- Подпись: `new ECDsaCng(key).SignData(data, HashAlgorithmName.SHA256)` — сразу P1363, 64 байта.
- `PRK` без доступа к `Z`: `new ECDiffieHellmanCng(agree) { KeyDerivationFunction = Hmac, HashAlgorithm = CngAlgorithm.Sha256, HmacKey = salt }.DeriveKeyMaterial(phoneAgree)`
  возвращает ровно `HMAC-SHA256(salt, Z)` = HKDF-Extract. `HmacKey` обязателен (`null` меняет смысл). Expand — `HMACSHA256`.
- AES-GCM — P/Invoke `bcrypt.dll`: `BCryptOpenAlgorithmProvider("AES")`, `BCryptSetProperty("ChainingMode", "ChainingModeGCM")`,
  `BCryptGenerateSymmetricKey`, `BCryptEncrypt`/`BCryptDecrypt` с `BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO`
  (`cbSize`, `dwInfoVersion = 1`, нонс, AAD, тег 16). Неверный тег — статус `0xC000A002`. Структура проверена под x64;
  сборку под x86 проверить тем же тестом векторов.
- Сравнение `tag` — свой цикл за постоянное время.

### Mobile — Android, minSdk 31

- Ключи: `KeyPairGenerator.getInstance("EC", "AndroidKeyStore")` с `KeyGenParameterSpec` (`ECGenParameterSpec("secp256r1")`;
  подпись — `PURPOSE_SIGN` + `DIGEST_SHA256`; согласование — `PURPOSE_AGREE_KEY`, API 31, F-3).
- Открытый ключ: `(public as ECPublicKey).w.affineX/affineY` — `BigInteger.toByteArray()` даёт 31–33 байта: обрезать
  ведущий 0 и дополнять нулями слева до 32. Ключ ПК — `KeyFactory("EC").generatePublic(ECPublicKeySpec(ECPoint(x, y), params P-256))`.
- `Z`: `KeyAgreement.getInstance("ECDH", "AndroidKeyStore")`, `init(agreeKey)`, `doPhase(pcAgree, true)`, `generateSecret()`.
  HKDF — `Mac("HmacSHA256")` вручную.
- Подпись: `Signature.getInstance("SHA256withECDSA")` с ключом Keystore даёт DER — перевести в P1363 (`r`, `s` без
  ведущего 0, слева нули до 32). В векторах у каждой подписи есть `der_hex` для теста перевода.
- AES-GCM: новый `Cipher.getInstance("AES/GCM/NoPadding")` на каждый конверт, `GCMParameterSpec(128, nonce)`,
  `updateAAD`, `doFinal` → шифртекст ‖ тег.
- Криптография — в `androidMain` (JCA), общие строки и разбор конверта — в `commonMain`.

### Векторы

`vectors/gen.py` (Python 3, `cryptography` ≥ 43 — детерминированная подпись RFC 6979 для стабильных файлов): без
аргументов пересчитывает всё и сверяет с файлами, плюс отрицательные случаи; `--write` перегенерирует. Файлы:

| Файл | Что | Кто обязан пройти |
|---|---|---|
| `keys.json` | четыре фиксированные пары: `d`, `x`, `y`, `public` | все: разбор и экспорт ключа |
| `pairing.json` | QR, `T`, `tag`, отпечаток, `Z`, `salt`, `PRK`, `K_pc`, `K_phone`; `reject` — неверные `tag`; `qr_reject` — QR, которые телефон отвергает | desktop (проверка `tag`, ключи), mobile (QR, `tag`, ключи) |
| `envelope.json` | конверты в обе стороны с ключом, нонсом, AAD и получателем `to`; `reject`, `reject_text` | desktop и mobile — шифрование с данным нонсом и расшифровка; server — `reject` без ключа |
| `auth.json` | строки входа и запросов, подписи (P1363 и DER), `verify` с верными и неверными подписями, окно повтора | server — всё; desktop и mobile — строки, перевод DER, своя подпись проверяется эталонным `verify` |

Тест блока читает JSON векторов из `protocol/vectors/` (не копирует значения в код) и для своих подписей проверяет, что
подпись, сделанная его ключом из `keys.json`, проходит `verify` (подписи ECDSA случайны, байты совпадать не обязаны).
Ключи из `keys.json` в Keystore не импортируются — mobile проверяет подпись и ECDH на программных ключах JCA из `keys.json`, а путь
Keystore — на устройстве: ключ Keystore подписывает, открытый ключ и подпись проходят эталонную проверку.
