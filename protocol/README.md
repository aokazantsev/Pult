# Протокол Pult

Версия протокола — `2`: сквозное шифрование, сопряжение по QR, вход «вызов — ответ» и подпись запросов. Ключи,
сопряжение, конверт, подпись и версии — [`CRYPTO.md`](CRYPTO.md) (нормативно, до байта), эталонные векторы —
[`vectors/`](vectors/); содержимое конвертов этапа 3 — [`MESSAGES.md`](MESSAGES.md). Здесь — запросы, поток SSE и сводка типов. Архитектура —
[`docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md), §4 (транспорт), §6 (протокол). Формат — JSON, UTF-8.

Версия 1 (этап 1: без шифрования, токены сторон в `pairs.json`) снята и не поддерживается.

## Транспорт

Сторона — `pc` или `phone`. Пути — от базового адреса сервера (на стенде `https://aokaztest.ru/pult`).

| Запрос | Подпись | Что делает |
|---|---|---|
| `GET /info` | — | `{"name":"pult-relay","protocol":[2]}` |
| `POST /v2/claims` | — | заявка ПК: `{"pc_sign","pc_agree"}` → `201 {"pair","ttl"}` (CRYPTO §3.1) |
| `POST /v2/claims/{pair}` | — | ключи телефона: `{"phone_sign","phone_agree","tag"}` → `200 {"pair"}` (CRYPTO §3.3) |
| `POST /v2/pairs/{pair}/challenge` | — | `{"from"}` → `200 {"challenge","ttl"}` (CRYPTO §4.1) |
| `GET /v2/pairs/{pair}/stream` | вход | поток SSE стороны (ниже, CRYPTO §4.2) |
| `POST /v2/pairs/{pair}/messages` | `messages` | отправить конверт; `202 {"seq":N,"dup":false}` |
| `POST /v2/pairs/{pair}/acks` | `acks` | подтвердить доставку: `{"ids":["<id>", ...]}`; `200 {"removed":N}` |
| `POST /v2/pairs/{pair}/ping` | `ping` | признак жизни стороны, тело пустое; `200` |
| `POST /v2/pairs/{pair}/delete` | `delete` | удалить пару: `{"reason"}`; `200` (CRYPTO §4.4) |
| `GET /v2/pairs/{pair}/state` | `state` | `pc_stream`, `phone_stream` (`open`/`closed`), `queued_to_pc`, `queued_to_phone` |

Подписанные запросы несут `Pult-From`, `Pult-Stream`, `Pult-N`, `Pult-Sig` (CRYPTO §4.3); поток — `Pult-From`,
`Pult-Challenge`, `Pult-Sig`.

Ошибки — `{"error":"<код>"}`:

| Код | Ошибки |
|---|---|
| 400 | `bad_envelope`, `bad_json`, `unsupported_version` (с `"protocol":[2]`), `bad_ack`, `bad_key`, `bad_tag`, `bad_header` (`Pult-N` не по форме), `bad_reason`, `bad_chunk` (битое chunked-тело) |
| 401 | `unauthorized` (нет заголовков), `bad_signature`, `stale_stream` |
| 404 | `not_found` |
| 409 | `claim_used`, `not_paired`, `replay` |
| 410 | `pair_deleted` (с `reason`, `by`) |
| 411 | `length_required` — тело без `Content-Length` и без `Transfer-Encoding: chunked` |
| 413 | `too_large` — тело больше 64 КБ, в том числе chunked |
| 429 | `queue_full`, `rate_limited` |
| 507 | `queue_bytes_full` — очередь получателя больше предела по байтам |

## Конверт

```json
{"v":2,"pair":"<pair>","from":"pc","id":"c0ffee-0001","ts":1793989146,"ttl":120,"ct":"<base64url>"}
```

Открытые поля — всё, что нужно серверу: `v` версия, `pair`, `from` отправитель, `id` идентификатор сообщения
(`[A-Za-z0-9_-]{1,64}`, уникален на всю пару), `ts` время отправителя в секундах (никто не сверяет), `ttl` срок жизни в
секундах. `ct` — тип и содержимое, зашифрованные ключом направления с аутентификацией открытых полей (CRYPTO §6).
Других полей нет. Сервер `ct` не читает.

Правила сервера:

- `ttl = 0` — мимо очереди: доставляется только открытому потоку получателя, иначе теряется. Для `thread`, `feed`,
  `snapshot`, `mode`.
- `ttl > 0` — до подтверждения доставки лежит в очереди на диске; верхняя граница срока — 900 с (обрезается только для
  очереди, в конверте получателю `ttl` исходный); очередь на получателя — до 200 сообщений (потом `429`) и до 4 МиБ (потом `507`); конверт — до
  64 КБ. Тело `POST` — с `Content-Length` или `Transfer-Encoding: chunked`.
- Повторный `id` подтверждается (`dup: true`) и не доставляется заново; память `id` переживает перезапуск сервера.
- Порядок: сообщения одной стороны доходят в порядке приёма по обоим путям (очередь и мимо неё) — один порядковый
  номер `seq` на пару, он же `id:` события SSE.

## Поток SSE

У стороны один поток: новый вход закрывает прежний. Первое событие — `session` (ниже). Сообщения получателю:

```
id: 17
event: message
data: {конверт}

```

При входе сервер шлёт `session`, затем служебные события, затем неподтверждённые сообщения очереди в порядке `seq`.
Неподтверждённое сообщение на открытом потоке повторно не шлётся; при следующем входе приходит снова, получатель
отбрасывает уже обработанные `id`. Каждые 15 с — комментарий `: keepalive`.

### Служебные сигналы сервера

```
event: server
data: {"type":"phone_stream","state":"open"}

```

| `type` | Кому | Поля |
|---|---|---|
| `session` | обоим | `stream` — идентификатор потока для подписи запросов (CRYPTO §4.2) |
| `pair` | ПК | `phone_sign`, `phone_agree`, `tag` — ключи телефона после скана QR (CRYPTO §3.3) |
| `phone_stream` | ПК | `state`: `open` / `closed` |
| `phone_incompatible` | ПК | `v` — версия отвергнутого конверта телефона |
| `intrusion` | обоим | — чужая попытка входа (CRYPTO §7) |
| `pair_deleted` | обоим | `reason`, `by` — пара удалена, поток закрывается |

`phone_stream`: ПК получает текущее состояние при входе — после неподтверждённых сообщений от телефона из очереди
(ARCHITECTURE §4; сервер пока шлёт его раньше — IMPLEMENTATION, этап 3, S2); затем сигнал при открытии первого потока телефона и при
его закрытии (D-60). Замена потока телефона в пределах порога живости сигнала не даёт. Сигнал «closed» идёт в потоке
ПК строго после всех сообщений, принятых от телефона раньше. Поток считается закрытым, если оборвано соединение либо от
стороны нет подписанного запроса (включая `ping`) дольше порога 45 с; клиент шлёт `ping` раз в 15 с.

## Типы сообщений (содержимое `ct`)

Нормативно — [`MESSAGES.md`](MESSAGES.md): поля, пределы, срок жизни, порядок, снимок, отрисовка; эталонные примеры —
[`vectors/messages.json`](vectors/messages.json). Сводка:

| `type` | Направление | `ttl` | Смысл |
|---|---|---|---|
| `hello` | оба | 120 | версии и возможности; у телефона ещё `feeds` — что из лент уже есть (CRYPTO §8, MESSAGES §6.1) |
| `thread` | ПК → телефон | 0 | описание треда: название, папка, статус, родитель, «стоит в диалоге на ПК» |
| `feed` | ПК → телефон | 0 | записи ленты треда с номером `seq` |
| `permission_request` / `permission_response` | ПК ↔ телефон | остаток ожидания / 600 | запрос разрешения и ответ |
| `choice_request` / `choice_response` | ПК ↔ телефон | остаток ожидания / 600 | вопрос с вариантами (`AskUserQuestion`) и ответ |
| `text_request` / `text_response` | ПК ↔ телефон | остаток ожидания / 600 | конец хода: окно текста и текст |
| `resolved` | ПК → телефон | 900 | исход запроса: `answered`, `expired`, `resolved_on_pc`, `unknown` |
| `mode` | ПК → телефон | 0 | режим `phone` / `pc` |
| `snapshot` | ПК → телефон | 0 | снимок: режим, треды, открытые запросы, исходы закрытых; части |

Тип `status` этапа 1 заменён `thread`; `unpair` и `notification` не используются (D-77). Неизвестный `type` получатель
показывает карточкой без действий (ARCHITECTURE §6.3).

## Исходы и подтверждения

Ответ телефона: `POST messages` → `202` (приём сервером) → карточка «отправлено, ждём ПК» → `resolved` от ПК. Телефон
подтверждает доставку запроса `POST acks` после показа; без подтверждения запрос остаётся в очереди до срока. Повтор
неподтверждённого `POST` — с тем же `id` конверта, новыми `Pult-N` и подписью (CRYPTO §4.3).
