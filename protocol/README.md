# Протокол Pult, этап 1

Версия протокола — `1`. Этап 1: без шифрования и подписи, пара задаётся вручную (токены сторон лежат на сервере в
`pairs.json`). Архитектура — [`docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md), §4 (транспорт), §6 (протокол).
Формат — JSON, UTF-8.

## Транспорт

Сторона — `pc` или `phone`. Токен стороны передаётся заголовком `Authorization: Bearer <token>`; по токену сервер
определяет пару и сторону. Этап 2 заменяет токен подписью «вызов — ответ».

| Запрос | Что делает |
|---|---|
| `GET /info` | `{"name":"pult-relay","protocol":[1]}`, без авторизации |
| `GET /v1/pairs/{pair}/stream` | поток SSE получателя (ниже) |
| `POST /v1/pairs/{pair}/messages` | отправить конверт; `202 {"seq":N,"dup":false}` |
| `POST /v1/pairs/{pair}/acks` | подтвердить доставку: `{"ids":["<id>", ...]}`; `200 {"removed":N}` |
| `POST /v1/pairs/{pair}/ping` | признак жизни стороны; `200` |
| `GET /v1/pairs/{pair}/state` | `pc_stream`, `phone_stream` (`open`/`closed`), `queued_to_pc`, `queued_to_phone` |

Ошибки — `{"error":"<код>"}`: `401 unauthorized`, `400 bad_envelope | bad_json | unsupported_version | bad_ack`,
`413 too_large`, `429 queue_full`, `404 not_found`.

## Конверт

```json
{
  "v": 1,
  "pair": "p1",
  "from": "pc",
  "id": "c0ffee-0001",
  "ts": 1793989146,
  "ttl": 120,
  "inner": {"type": "permission_request", "...": "..."}
}
```

Открытые поля — всё, что нужно серверу: `v` версия, `pair`, `from` отправитель, `id` идентификатор сообщения
(уникален на всю пару, до 64 символов), `ts` время отправителя в секундах (сервер не сверяет), `ttl` срок жизни в
секундах. Внутри — `inner`: тип и содержимое. Сервер `inner` не читает.

Этап 2: `inner` заменяется полем `ct` (шифртекст с аутентификацией открытых полей), добавляется `sig`; сервер уже
принимает конверт с `ct` вместо `inner`.

Правила сервера:

- `ttl = 0` — мимо очереди: доставляется только открытому потоку получателя, иначе теряется. Для `status`, `feed`,
  `snapshot`, `mode`.
- `ttl > 0` — до подтверждения доставки лежит в очереди на диске; верхняя граница срока — 900 с (сверху обрезается);
  очередь на получателя — до 200 сообщений, потом `429`; конверт — до 64 КБ.
- Повторный `id` подтверждается (`dup: true`) и не доставляется заново; память `id` переживает перезапуск сервера.
- Порядок: сообщения одной стороны доходят в порядке приёма по обоим путям (очередь и мимо неё) — один порядковый
  номер `seq` на пару, он же `id:` события SSE.

## Поток SSE

У стороны один поток: новый вход закрывает прежний. Сообщения получателю:

```
id: 17
event: message
data: {конверт}

```

При входе сервер сначала шлёт служебное событие (только ПК), затем неподтверждённые сообщения очереди в порядке `seq`.
Неподтверждённое сообщение на открытом потоке повторно не шлётся; при следующем входе приходит снова, получатель
отбрасывает уже обработанные `id`. Каждые 15 с — комментарий `: keepalive`.

### Служебные сигналы сервера (только ПК)

```
event: server
data: {"type":"phone_stream","state":"open"}

```

`state` — `open` или `closed`. ПК получает текущее состояние сразу при входе; затем сигнал при открытии первого потока
телефона и при его закрытии (D-60). Замена потока телефона в пределах порога живости сигнала не даёт. Сигнал
«closed» идёт в потоке ПК строго после всех сообщений, принятых от телефона раньше. Поток считается закрытым, если
оборвано соединение либо от стороны нет `POST` (включая `ping`) дольше порога 45 с; клиент шлёт `ping` раз в 15 с.

## Типы `inner` (этап 1)

Общее: `inner.type` и поля ниже. `request_id` — идентификатор запроса, уникален на сессию. `thread` — идентификатор
треда и `title` (необязательно) для показа.

ПК → телефон:

| `type` | Поля | Смысл |
|---|---|---|
| `permission_request` | `request_id`, `thread`, `title`, `tool`, `summary`, `input` (обрезан) | запрос разрешения |
| `choice_request` | `request_id`, `thread`, `title`, `question`, `options: [{id,label}]`, `multi` | вопрос с вариантами |
| `text_request` | `request_id`, `thread`, `title`, `last_message` | конец хода, окно текста |
| `resolved` | `request_id`, `outcome` | исход запроса |
| `status` | `thread`, `status` | статус треда (`working`, `done`, `error`) — ttl 0 |
| `mode` | `mode` (`phone`/`pc`) | режим — ttl 0 |

`outcome`: `answered` (ответ принят), `expired` (истёк), `resolved_on_pc`, `unknown`.

Телефон → ПК:

| `type` | Поля | Смысл |
|---|---|---|
| `permission_response` | `request_id`, `decision` (`allow`/`deny`), `reason` | ответ |
| `choice_response` | `request_id`, `selected: [id]` | ответ |
| `text_response` | `request_id`, `text` | текст, продолжение хода |
| `hello` | `protocol`, `capabilities: []` | при каждом подключении телефона |

Неизвестный `type` получатель показывает карточкой без действий (ARCHITECTURE §6.3); `snapshot` и `feed` — этап 3.

## Исходы и подтверждения

Ответ телефона: `POST messages` → `202` (приём сервером) → карточка «отправлено, ждём ПК» → `resolved` от ПК. ПК
подтверждает доставку запроса `POST acks` после показа; без подтверждения запрос остаётся в очереди до срока.
