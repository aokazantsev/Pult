# Pult, этап 3: сообщения внутри конверта

Нормативная спецификация содержимого `ct` (CRYPTO §6): треды, лента, запросы, режим, снимок, переподключение, конец
сессии, вход на телефоне и отрисовка ленты. Реализации desktop и mobile делаются строго по ней и обязаны пройти
эталонные примеры [`vectors/messages.json`](vectors/messages.json) своим тестом (§11). Конверт, ключи и подпись —
[`CRYPTO.md`](CRYPTO.md), запросы к серверу и поток — [`README.md`](README.md), поведение —
[`docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md) §5–§7, решения — D-77…D-91 в
[`docs/DECISIONS.md`](../docs/DECISIONS.md).

Слова «обязан», «нельзя» — требования. Где этот документ расходится с ARCHITECTURE в форме сообщений, прав этот
документ; в поведении — ARCHITECTURE, а расхождение — ошибка документа.

## 1. Общее

### 1.1. Форма

- Открытый текст конверта — объект JSON в UTF-8 с полем `type`. Повторные ключи отвергаются (CRYPTO §1).
- Необязательное поле либо есть со значением своего типа, либо его нет: `null` не используется ни в одном поле.
  Сообщение с `null`, с полем не того типа или без обязательного поля получатель отбрасывает целиком (журнал, без
  карточки) и подтверждает, как негодный конверт (D-71). Так же отбрасывается сообщение, нарушающее пределы длины,
  числа элементов или порядок `seq` из разделов ниже: отправитель обязан их соблюдать.
- **Незнакомые поля** получатель пропускает: так ПК можно обновлять раньше телефона. Незнакомый `type` — карточка без
  действий с названием типа (ARCHITECTURE §6.3), незнакомое значение перечисления — правило поля ниже; у необязательных `via` и `turn_note` без своего правила — как
  будто поля нет; незнакомый `direction` — запись `peer` без стрелки направления; незнакомый `kind` исхода — закрытая
  карточка «Запрос» с `summary`. Сообщение при этом не отбрасывается. Известный тип,
  пришедший не в ту сторону (ответ телефона — телефону, `feed` — ПК), отбрасывается.
- Идентификаторы (`thread`, `request_id`, `call`, `snapshot`, `id` вопросов и вариантов) — `[A-Za-z0-9_-]{1,64}`, как
  идентификаторы CRYPTO §1. Числовые поля протокола — целые от 0 до 2^53−1, как там же; значения аргументов `input`
  (§4.2) — любые числа JSON. Строковые перечисления (`status`, `kind`, `outcome`, `mode`, `via`, `direction`,
  `turn_note`, `decision`) — до 64 символов.
- Пробельные символы — `White_Space` Юникода: U+0009–U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000–U+200A, U+2028,
  U+2029, U+202F, U+205F, U+3000. «Непустая» строка — в ней есть символ не из этого набора.
- Длины строк ниже — в символах Юникода (кодовых точках), не в байтах. Обрезка — по границе кодовой точки, обрезанная
  строка кончается на `…` (U+2026) и считается в пределе; у записи ленты с обрезанным полем — `"truncated": true`.

### 1.2. Пределы размера

| Что | Предел | Почему |
|---|---|---|
| открытый текст одного сообщения (сериализованный JSON) | **48 000 байт** | конверт до 65 536 байт (сервер, `PULT_MAX_ENVELOPE`): `ct` — base64url от `nonce ‖ текст ‖ тег`, ×4/3, плюс открытые поля |
| один элемент: запись ленты, запрос, исход, описание треда (сериализованный JSON) | **16 384 байт** | в сообщение всегда помещается хотя бы один элемент |

Отправитель режет поля до перечисленных в разделах пределов, а если элемент всё ещё больше 16 384 байт — режет самое
длинное строковое поле элемента вдвое, пока не уложится. Сообщение из нескольких элементов (`feed`, части `snapshot`)
отправитель набирает до 48 000 байт и продолжает следующим сообщением.

### 1.3. Срок жизни конвертов

| Сообщения | `ttl` | Почему |
|---|---|---|
| `thread`, `feed`, `mode`, `snapshot` | 0 — мимо очереди | состояние: пропущенное восполняет снимок (§7) |
| `permission_request`, `choice_request`, `text_request` | остаток ожидания Pult (ARCHITECTURE §2), целые секунды вверх, не меньше 1; у `answerable: false` — всё ожидание Pult от создания | запрос не должен пережить своё ожидание; у `answerable: false` хук уже отпущен, карточка живёт ожидание Pult или до ответа на ПК (§4.3) |
| `resolved` | 900 (потолок сервера) | исход должен дойти до телефона, вернувшегося на экран |
| `permission_response`, `choice_response`, `text_response` | 600 | дольше любого ожидания хука (до 540 с) |
| `hello` | 120 (D-72) | — |

Закрывает пункт этапа 2 «классы срока жизни служебных сообщений» (D-85). Сигналы сервера (`intrusion` и другие) —
не конверты, срока у них нет.

### 1.4. Порядок

- **ПК отправляет сообщения одной упорядоченной очередью**: следующий `POST messages` уходит только после ответа
  сервера на предыдущий; повтор после ошибки сети держит очередь (тот же `id`, CRYPTO §4.3). Сервер сохраняет порядок
  одной стороны по обоим путям (README, «Конверт»), поэтому телефон получает сообщения ПК в порядке их постановки в
  очередь.
- Телефон отправляет так же.
- ПК ставит описание треда (`thread`) в очередь раньше первой записи ленты и первого запроса этого треда. Телефон,
  получивший запись или запрос незнакомого треда (описание потерялось при `ttl` 0), заводит тред-заготовку с `title`
  запроса или `…` до следующего снимка.

### 1.5. Возможности и совместимость

- `hello.capabilities` ПК — `[]`. Телефон этапа 3 объявляет `["choice"]`: умеет отвечать на `choice_request` с
  `answerable: true`. Без `choice` ПК вопрос на телефон не шлёт, он сразу уходит в обычный диалог ПК (ARCHITECTURE §6.3).
- Номер версии протокола остаётся **2** (D-69): этап 3 меняет только содержимое `ct`. Тип `status` этапа 1 заменён
  `thread`, типы `unpair` и `notification` не используются (D-77). Выпуска до этапа 4 нет, поэтому совместимость
  промежуточных сборок этапов 2 и 3 между собой не поддерживается.

## 2. Треды

### 2.1. Идентификатор

`thread` — непрозрачный идентификатор ПК для пункта списка тредов. ПК выбирает его сам и держит неизменным, пока это
тот же пункт: продолжение треда агентом с новым идентификатором (D-37) — тот же `thread`; форк и тред, родство которого
не определилось, — новый. Новый пункт получает новый случайный идентификатор (16 случайных байт в base64url): `thread`
в сессии не переиспользуется, в том числе после перезапуска ПК и вычёркивания (§2.5). Телефон в идентификатор не
заглядывает.

**Неизменность пары (`thread`, `seq`).** В пределах сессии запись ленты с данными `thread` и `seq` всегда одна и та
же (§3.2). ПК, который не может этого гарантировать (потерял или не прочёл своё состояние треда после перезапуска),
обязан дать пункту новый `thread`: старый пункт уйдёт с телефона по следующему снимку (§6.4), новый начнёт ленту
заново с пометки `notice` «Pult на ПК перезапущен, часть ленты потеряна» (D-78).

### 2.2. Описание треда

```json
{"thread":"t1","title":"Правка README","folder":"Pult","status":"working","pc_dialog":false}
```

| Поле | Обяз. | Что |
|---|---|---|
| `thread` | да | идентификатор (§2.1) |
| `title` | да | название, одна строка до 120 символов: из данных агента (F-11), иначе первое сообщение пользователя; непустая (§1.1): нечего показать — `…` |
| `folder` | да | папка проекта, как на экране QR: имя последней папки пути, до 120 символов (D-59) |
| `status` | да | ниже |
| `pc_dialog` | да | «стоит в диалоге на ПК» (§2.4) |
| `error` | нет | только при `status: error`: код ошибки агента (`StopFailure.error`, F-16), до 64 символов |
| `parent` | нет | `thread` родителя, если родитель в сессии (D-46) |
| `fork_of` | нет | `{"title": "<до 120>", "thread": "<id>"}` — источник форка; `thread` есть, только если источник в сессии |
| `turn_note` | нет | `continuation_cap` — ход кончился без окна текста из-за предела продолжений (D-61); снимается со следующим `working` |
| `last_seq` | только в снимке | `seq` последней записи ленты треда, `0` — записей нет (§6.4) |

`status`:

| Значение | Когда (Claude Code) | Телефон показывает |
|---|---|---|
| `unknown` | родитель, выведенный ради дочернего, без собственных событий после сопряжения (ARCHITECTURE §5.2) | «нет событий» |
| `working` | `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure`, хук взял ответ телефона (`answered`) | «работает» |
| `done` | `Stop` | «закончил» |
| `error` | `StopFailure` | «ошибка» и `error` |
| `ended` | `SessionEnd` | «закрыт» |

Статус меняют только события хуков. После отказа или прерывания хода на ПК хука нет (F-7): тред показывает «работает»
до следующего события — принятое ограничение (D-91, ARCHITECTURE §9). Незнакомое значение телефон показывает как
`unknown`.

### 2.3. Сообщение `thread`

`{"type": "thread", ...описание без last_seq}` — полное описание треда, заменяет прежнее целиком. ПК шлёт его при
появлении треда в сессии и при каждом изменении любого поля, кроме `last_seq`. Порядок — §1.4.

### 2.4. Отметки

- **«Ждёт действия»** и **«ждёт текста»** телефон выводит сам из своих незакрытых карточек треда (`open`, `sending`, `sent`, §4.6): есть такой
  `permission_request` или `choice_request` с `answerable: true` — «ждёт действия»; есть такой `text_request` —
  «ждёт текста». Отдельного поля нет: отметка не может разойтись с карточкой (D-80).
- **«Стоит в диалоге на ПК»** — поле `pc_dialog`, его ведёт ПК по правилам ARCHITECTURE §5.2 и D-34: телефон этого
  вывести не может (запрос мог уйти в диалог, не побывав на телефоне). Снимает её и исход `answered`: диалог
  desktop-приложения закрывается вместе с хуком, взявшим ответ телефона (F-20).
- **Сводная отметка родителя** — телефон выводит сам: у родителя видна «ждёт действия» или «ждёт текста», если она есть
  у него или у любого его потомка по `parent`.
- **«Окно закрыто»** — исход `text_request`, отличный от `answered` (§4.5); при `turn_note: continuation_cap` — «окно
  текста не открыто: предел продолжений подряд, ответ — на ПК».

### 2.5. Состав

- Тред входит в сессию по правилам D-57/D-59; о треде вне сессии телефону не уходит ничего.
- Субагенты внутри треда (инструмент `Agent`, события с `agent_id`, F-14) — не отдельные треды: их вызов и итог —
  записи `tool_call` / `tool_result` ленты родителя (D-79).
- В сессии не больше **100** тредов: при появлении сто первого ПК вычёркивает тред с самым давним последним событием
  среди `ended`, иначе среди всех, кроме тредов с открытым запросом; вычеркнутый тред уходит с телефона по следующему
  снимку, его новое событие делает его новым пунктом с новым `thread`.

## 3. Лента

### 3.1. Сообщение `feed`

```json
{"type":"feed","thread":"t1","entries":[{"seq":1,"kind":"user","text":"Поправь README"}]}
```

`entries` — непустой массив записей одного треда с подряд идущими `seq` по возрастанию. Лента только дополняется:
записи не меняются и не удаляются.

### 3.2. Порядковый номер

`seq` — номер записи в треде: первая запись треда в сессии — 1, каждая следующая на 1 больше, без пропусков, включая
`unrecognized` и `notice`. Номер даёт ПК и не переиспользует (§2.1). По `seq` телефон стыкует снимок с лентой и видит
пропуски (§6.5).

### 3.3. Записи

Общие поля: `seq` (да), `kind` (да), `at` (нет: время записи транскрипта, секунды Unix по часам ПК), `truncated` (нет,
`true`, если поле записи обрезано).

| `kind` | Поля | Что | Отрисовка (§9) |
|---|---|---|---|
| `user` | `text` (до 8000); `via: "phone"` и `request_id` (нет) | сообщение пользователя. Текст, принятый с телефона хуком окончания хода, — эта же запись с `via` и `request_id` его `text_request`: в транскрипте он появляется отзывом хука, адаптер распознаёт его и снимает служебный префикс агента | простой текст |
| `assistant` | `text` (до 8000) | сообщение агента; ход рассуждений модели (`thinking`) не передаётся | разметка |
| `tool_call` | `call`, `tool` (до 64), `summary` (до 300), `input` (объект, нет) | вызов инструмента; `input` — как у `permission_request` (§4.2) | моноширинно |
| `tool_result` | `call`, `output` (до 2000), `error` (`true`/`false`) | итог вызова `call` | моноширинно |
| `peer` | `direction` (`in`/`out`), `peer_title` (до 120), `text` (до 8000), `peer` (нет: `thread`, если собеседник в сессии) | сообщение между тредами: в ленте получателя `in`, отправителя `out` (D-46) | простой текст |
| `notice` | `text` (до 300) | служебная строка ПК: «Запрос прерван на ПК», «Контекст сжат», «Pult на ПК перезапущен, часть ленты потеряна» | простой текст, приглушённо |
| `unrecognized` | `count` (≥ 1) | столько записей транскрипта подряд адаптер не распознал (D-47) | «часть записей не распознана (N)» |

- `call` — идентификатор вызова (у Claude Code — `tool_use_id`; не подходит под формат — ПК заменяет своим), связывает
  `tool_result` с `tool_call`. `tool_result` без известного телефону `tool_call` рисуется отдельно.
- `unrecognized` ставится на каждую подряд идущую серию пропущенных записей, прочитанную за один проход; соседние
  такие записи телефон может слить в одну плашку.
- Какие записи выдаются: кандидаты в ленту — записи транскрипта с `uuid` и временем (`timestamp`, часы того же ПК);
  записи без них — служебные (`queue-operation`, `custom-title` и подобные), в ленту не идут и нераспознанными не
  считаются (F-22). Кандидат выдаётся, только если его время не раньше сопряжения и его `uuid` ещё не выдан в этой
  сессии ни в одном пункте. Копия истории в транскрипте продолжения или форка сохраняет `uuid` и время (F-22), поэтому
  история до сопряжения и уже показанное не выдаются (D-30, D-35), а первое сообщение треда, вошедшего в сессию, не
  теряется. `unrecognized` считается только среди кандидатов, прошедших отбор; кандидат, ушедший в `unrecognized`, тоже
  считается выданным.
- Незнакомый телефону `kind` рисуется как `unrecognized` с `count` 1.

## 4. Запросы

### 4.1. Общие поля

| Поле | Что |
|---|---|
| `request_id` | идентификатор запроса, уникален на сессию |
| `thread` | тред |
| `title` | название треда на момент запроса — для треда, описание которого телефон не получил (§1.4) |
| `after_seq` | `seq` последней записи ленты треда, выданной ПК до создания запроса, `0` — записей нет; телефон ставит карточку в ленте после неё |

Пары «запрос — ответ»: `permission_request` → `permission_response`, `choice_request` → `choice_response`,
`text_request` → `text_response`. Исход любого запроса — `resolved` (§4.5).

### 4.2. Разрешение

`permission_request`: общие поля, `tool` (до 64), `summary` (до 300), `input` — объект аргументов инструмента: строки
до 1000 символов, вложенные объекты и массивы — строкой их JSON до 1000 символов, числа и `true`/`false` как есть;
аргумент со значением `null` отправитель опускает.

`permission_response`: `request_id`, `decision` — `allow` или `deny` (другое значение — ответ отбрасывается: ПК решение не
угадывает), `reason` (нет, до 1000) — текст отказа для агента.

### 4.3. Вопрос с вариантами

`choice_request` — вопрос инструмента `AskUserQuestion` (F-2):

```json
{"type":"choice_request","request_id":"r2","thread":"t1","title":"Правка README","after_seq":4,"answerable":true,
 "questions":[{"id":"q1","header":"Формат","question":"В каком формате?","multi":false,"other":true,
   "options":[{"id":"o1","label":"Markdown","description":"как сейчас"},{"id":"o2","label":"HTML"}]}]}
```

| Поле | Что |
|---|---|
| `answerable` | `true` — телефон может ответить; `false` — адаптер не умеет передать ответ: хук сразу вернул «нет решения», вопрос стоит в диалоге ПК, карточка без действий (ARCHITECTURE §5.3). ПК закрывает её по общим поводам: `resolved_on_pc` — ответ на ПК (как у разрешения, ARCHITECTURE §5.3 п. 7) или переключение в режим ПК; без них — `expired` через ожидание Pult от создания |
| `questions` | 1–4 вопроса |
| `questions[].id` | идентификатор вопроса, в запросе не повторяется |
| `questions[].header` | нет; короткая метка до 50 |
| `questions[].question` | текст до 500 |
| `questions[].multi` | можно выбрать несколько |
| `questions[].other` | можно ответить своим текстом («Другое») |
| `questions[].options` | 1–8 вариантов: `id` (в вопросе не повторяется), `label` (до 100), `description` (нет, до 300) |

`choice_response`:

```json
{"type":"choice_response","request_id":"r2","answers":[{"question":"q1","selected":["o1"]}]}
```

`answers` — по одному элементу на **каждый** вопрос запроса: `question` — его `id`, `selected` — массив `id` его
вариантов без повторов, `other` (нет) — свой текст до 2000 символов, непустой после обрезки пробелов, только при
`other: true`. Вопрос с `multi: false` — ровно одно из двух: один `id` в `selected` или `other` при пустом `selected`.
Вопрос с `multi: true` — выбранные варианты, `other` или то и другое вместе, но не пусто. Ответ, нарушающий любое из этих правил, ответ на
`answerable: false` и ответ телефона без возможности `choice` ПК отбрасывает с записью в журнал; запрос остаётся
открытым до срока (D-86). Как ответ уходит агенту (метки вариантов, `other`, `updatedInput`), — дело адаптера.

### 4.4. Окно текста

`text_request`: общие поля, `last_message` — последнее сообщение агента, до 4000 символов, разметка (§9).

`text_response`: `request_id`, `text` — непустой после обрезки пробелов, до 8000 символов (поле ввода телефона больше не
принимает). Принятый текст появится в ленте записью `user` с `via: "phone"` (§3.3): карточка ответа его не дублирует.

Окно открыто, только пока поток телефона открыт (D-58); `text_request` уходит, только когда ПК считает поток открытым, —
это поведение ПК, а не срок конверта (§1.3).

### 4.5. Исход

`resolved`: `request_id`, `outcome`:

| `outcome` | Когда (ARCHITECTURE §5.3) | Телефон |
|---|---|---|
| `answered` | хук взял ответ телефона | «принято» |
| `expired` | срок, отказ хука, ответ на неизвестный запрос, закрытие потока для окна текста, перезапуск ПК до передачи решения (§6.6); у `answerable: false` — прошло ожидание Pult, вопрос остаётся в диалоге ПК (`pc_dialog`) | «истёк»; окно текста — «окно закрыто» |
| `resolved_on_pc` | ответ или ввод на ПК, переключение в режим ПК, сообщение другого треда в окно текста | «решено на ПК» |
| `unknown` | решение передано хуку, а подтверждения нет: обрыв канала, пропажа хука, перезапуск ПК (D-40) | «неизвестно, могло выполниться» |

Незнакомое значение телефон показывает как `unknown`. **Первый `resolved` по запросу окончательный**; ПК на ответ к уже
закрытому запросу присылает `resolved` с его записанным исходом, на ответ к запросу, которого не знает, — `expired`.

Окно текста с исходом не `answered` возвращает отправленный текст в поле ввода черновиком: текст не теряется
(IMPLEMENTATION, этап 3). Черновик живёт в памяти процесса до отправки или разрыва.

### 4.6. Карточка запроса на телефоне

| Состояние | Переход |
|---|---|
| `open` | пришёл запрос или он есть в снимке среди открытых |
| `sending` | пользователь ответил; ответ ждёт `202` сервера, повторы — тем же `id` конверта (README, «Исходы») |
| `sent` | сервер принял ответ (`202`): «отправлено, ждём ПК» |
| `closed(outcome)` | пришёл `resolved` или исход в снимке; окончательно |
| `missing` | запроса нет в полном снимке ни среди открытых, ни среди исходов (§6.4): показывается как «неизвестен»; следующий `resolved` или исход снимка закрывает его своим исходом, запрос среди открытых в снимке возвращает в `open` |

Действия есть только в `open`. «Ждёт действия» / «ждёт текста» (§2.4) считаются по `open`, `sending` и `sent`. Пришедший
повторно запрос того же `request_id` не возвращает карточку из `sending`, `sent` или `closed` в `open`.

## 5. Режим

`mode`: `mode` — `phone` или `pc`. ПК шлёт его после своего входа, при каждом переключении и в части 1 снимка. Телефон
показывает режим, но не меняет его (D-17). Незнакомое значение — «режим неизвестен».

## 6. `hello`, снимок и порядок

### 6.1. `hello`

`{"type":"hello","protocol":[2],"capabilities":[...]}` — CRYPTO §8. Телефон добавляет `feeds` — что у него уже есть:

```json
{"type":"hello","protocol":[2],"capabilities":["choice"],"feeds":[{"thread":"t1","seq":40}]}
```

`seq` — наибольший номер, до которого у телефона нет дыр, начиная с самой ранней хранимой записи треда: есть 1…40 и
45…50 — `40`. Если между этим номером и наибольшим хранимым больше 200, шлётся наибольший хранимый: такую дыру
хвост (§6.5) всё равно не закроет, а повтор уже имеющихся записей съел бы бюджет хвостов. Тред, которого у телефона нет, в `feeds` не входит; пустой список — `[]`. ПК `feeds` не шлёт.

Телефон шлёт `hello` при каждом открытии потока (после события `session`), без ограничения частоты. Повторный `hello`
на том же потоке — просьба о снимке: когда сборка снимка отброшена (§6.4) или за 10 с после ответа `202` на свой
`hello` не пришла часть 1 снимка. Повторный — не чаще раза в 10 с и не больше 3 на поток; дальше телефон ждёт
следующего открытия потока и считает отброшенное в сводной карточке (D-71). ПК на каждый `hello` телефона отвечает
снимком; несколько `hello` за 1 с — один снимок.

### 6.2. Когда ПК шлёт снимок

- на `hello` телефона;
- после своего входа в поток, если пара активна (ARCHITECTURE §5.2);
- сразу после своего `hello` при сопряжении.

### 6.3. Сообщение `snapshot`

Снимок — одна или несколько частей, у всех общий `snapshot` (идентификатор снимка, уникален на сессию):

| Поле | Обяз. | Что |
|---|---|---|
| `snapshot` | да | идентификатор снимка |
| `part` | да | номер части с 1 |
| `last` | да | `true` у последней части |
| `mode` | в части 1 | режим (§5) |
| `threads` | нет | описания тредов с `last_seq` (§2.2) |
| `requests` | нет | открытые запросы, сообщение которых ПК поставил в очередь телефону: полные объекты, как в их сообщениях, с `type` |
| `outcomes` | нет | исходы закрытых запросов (ниже) |

**Состав — только обязательное состояние; хвостов ленты в снимке нет.** ПК заполняет части в порядке: `mode`, все
`threads`, все `requests`, все `outcomes`, каждую до 48 000 байт; массив, не поместившийся в часть, продолжается в
следующей. Хвосты лент идут после последней части обычными `feed` (§6.5) — им достаётся остаток (D-81).

**Исход** в `outcomes`:

```json
{"request_id":"r1","kind":"permission","thread":"t1","after_seq":3,"summary":"Bash: mkdir t1","outcome":"expired"}
```

`kind` — `permission`, `choice`, `text`; `summary` — до 120 символов, для карточки запроса, которого телефон не видел.
В `outcomes` — исходы **последних 50 закрытых запросов сессии**, ушедших на телефон, по времени закрытия, старые
первыми. Подтверждения доставки отправитель не видит (`acks` уходит серверу), поэтому правило «после последнего снимка с
подтверждённой доставкой» (D-49) заменено окном последних 50 (D-82).

**Сборка снимка атомарна** относительно состояния ПК: снимок отражает состояние на один момент, и все его части ПК
ставит в очередь отправки (§1.4) под той же блокировкой, что и изменения состояния. Запрос, созданный после этого
момента, уходит в очереди после последней части; запрос, созданный раньше и ещё открытый, есть в `requests`, даже
если его сообщение уже ушло. Так гонка `hello` / запрос не закрывает новый запрос как `missing` (D-83).

### 6.4. Применение снимка на телефоне

Телефон собирает части одного `snapshot`: часть 1 начинает сборку (незаконченная сборка прежнего снимка
отбрасывается), каждая следующая обязана иметь тот же `snapshot` и номер на 1 больше, часть с `last: true` заканчивает.
Часть с номером больше 1 не по этому правилу (пропуск номера, другой `snapshot`) отбрасывает сборку: состояние остаётся
прежним, телефон повторяет `hello` (§6.1). Собранный снимок применяется целиком, по шагам:

1. Режим — из `mode`.
2. Список тредов заменяется `threads`: тред, которого в снимке нет, уходит со всей лентой и карточками; новый
   появляется; описания обновляются. `last_seq` запоминается для пометок (§6.5).
3. Каждый запрос `requests`: незнакомый — карточка `open`; знакомый в `open`, `sending`, `sent` — без изменений; в
   `missing` — снова `open`; в `closed` — без изменений (исход окончательный).
4. Каждый исход `outcomes` треда из `threads` (исход треда, которого в снимке нет, пропускается): знакомый запрос не в
   `closed` (в том числе `missing`) — `closed(outcome)`; незнакомый — закрытая карточка с
   `summary` после `after_seq` (запрос истёк, пока приложение было не на экране).
5. Карточка в `open`, `sending` или `sent`, которой нет ни в `requests`, ни в `outcomes`, — `missing` (§4.6): запрос
   потерян на ПК.

Пример на каждый шаг — `vectors/messages.json`, `snapshot_cases`.

### 6.5. Хвосты лент и пропуски

После последней части снимка ПК шлёт `feed` по каждому треду снимка:

- тред есть в `feeds` последнего `hello` телефона — записи с `seq + 1` до `last_seq`, но не больше последних **200**;
- треда в `feeds` нет — последние **50** записей;
- на все хвосты одного снимка — не больше **1 МиБ** открытого текста: сначала треды с открытыми запросами, затем по
  давности последнего события, свежие первыми; тред, чей хвост целиком не помещается в остаток, хвоста не получает,
  следующие треды ещё могут поместиться.

ПК после своего входа (§6.2) берёт `feeds` из последнего полученного `hello` телефона, сдвинутые на записи, которые он
с тех пор отправил с ответом `202`, пока считал поток телефона открытым (D-81).

Телефон хранит записи по `seq`, не больше последних **500** на тред (старые вытесняются), и принимает каждую запись
`feed` так: `seq`, который уже есть, пропускается (запись неизменна, §3.2); новый вставляется на своё место. Пометки
выводит из номеров:

| Где | Условие | Пометка |
|---|---|---|
| между записями | соседние хранимые `seq` отличаются больше чем на 1 | «пропущены записи (N)» |
| в начале | наименьший хранимый `seq` больше 1 | «ранние записи не показаны» |
| в конце | `last_seq` последнего снимка больше наибольшего хранимого | «последние записи не загружены» |

Пометка исчезает, когда дыру закрыли пришедшие записи. Молча дыра не остаётся ни в каком случае.

### 6.6. Перезапуск ПК

ПК хранит на диске, пока жива сессия: запись пары (этап 2) вместе с отмеченными папками и временем сопряжения — без
неё сессии нет; отдельным файлом состояния — описания тредов и их состояние ленты (§2.1) с выданными `uuid` (§3.3) и последними 200
записями каждого треда (из них строятся хвосты §6.5),
открытые запросы с отметкой, передано ли решение хуку, исходы последних 50 закрытых и последний `hello` телефона (версии,
возможности, `feeds`: после перезапуска ПК телефон, чей поток не рвался, `hello` не повторяет). Запись — до действия:
состояние треда с новым `seq` — до постановки записи в очередь, запрос — до постановки его сообщения, отметка «решение
передано» — до передачи хуку. При старте с живой сессией каждый запрос,
открытый на момент остановки, закрывается: решение хуку не передавалось — `expired`, передавалось без подтверждения —
`unknown` (D-40); ПК шлёт по каждому `resolved` и вносит исход в `outcomes` (D-84). Хуки этих запросов, потеряв канал,
сами возвращают агенту «нет решения». Нет файла состояния или он не читается — ПК начинает треды под новыми `thread` (§2.1):
старые уходят с телефона по снимку вместе со своими карточками, новые начинаются с `notice`. События хуков, пришедшие,
пока приём ПК не работал, теряются: статус треда после старта — сохранённый, до следующего события треда. `pc_dialog`
после старта: запрос разрешения или вопрос, закрытый `expired`, отдан диалогу (ARCHITECTURE §5.2) и ставит отметку;
закрытый `unknown` и окно текста отметку не меняют — остаётся сохранённое значение. Снимает её то же, что обычно (§2.4),
а также любое следующее событие хука треда, кроме уведомления о показе диалога (F-18): слежение за транскриптом
закрытого запроса после старта не идёт. После отказа на ПК хука нет (F-7), и отметка держится до следующего события
треда (принятое ограничение перезапуска).

## 7. Переподключение: «после обрыва ничего не пропало»

- Обрыв потока телефона: телефон входит заново (CRYPTO §4) и шлёт `hello` с `feeds`; из очереди сервера приходят
  неподтверждённые запросы, ответы и исходы (`ttl` > 0), затем снимок и хвосты. `Last-Event-ID` не используется: `id:`
  событий SSE — `seq` сервера на пару, а сообщения с `ttl` 0, пропущенные на мёртвом потоке, сервер не хранит; их
  восполняет снимок.
- Обрыв потока ПК: ПК входит заново, шлёт `mode`, снимок и хвосты (§6.2, §6.5). Записи ленты, появившиеся, пока ПК был
  без связи, получают `seq` как обычно и уходят хвостом.
- **Гарантия.** После переподключения у телефона точно те же режим, треды, отметки и открытые запросы, что у ПК в
  момент снимка; исходы последних 50 закрытых запросов; лента без молчаливых дыр — пропущенное до 200 записей на тред
  (в пределах 1 МиБ на снимок) приходит, остальное видно пометкой (§6.5).
- Отбор порогов: живость потока 45 с и `ping` раз в 15 с — этап 1 (README, «Поток SSE»).

## 8. Сессия

### 8.1. Поводы разрыва

Сообщения `unpair` нет (D-77): рвущая сторона удаляет пару подписанным запросом с причиной (CRYPTO §4.4), вторая
сторона узнаёт причину сигналом `pair_deleted` в открытом потоке или ответом `410` при входе; после срока хранения
причины (7 суток, D-73) — `404 not_found`. Причина видна серверу (D-50).

| `reason` | `by` | Кто и когда | Телефон показывает | ПК показывает |
|---|---|---|---|---|
| `user` | `pc` | «Разорвать» на ПК | «Сессию разорвали на ПК» | «Сессия разорвана» |
| `user` | `phone` | «Отвязать» на телефоне | «Телефон отвязан» | «Телефон отвязан с телефона» |
| `idle` | `pc` | простой N без событий тредов сессии (D-22, D-33) | «Сессия закрыта: нет событий <N>» | то же |
| `replaced` | `pc` | новое сопряжение на ПК | «На ПК начата новая сессия» | — |
| `replaced` | `phone` | новое сопряжение на телефоне | — | «Телефон сопряжён заново» |
| `pairing_rejected` | `pc` | `tag` не сошёлся (CRYPTO §3.4) | «ПК отклонил сопряжение: проверка не прошла» | «Попытка сопряжения не прошла проверку» |
| `no_hello` | `phone` | нет `hello` за 120 с (CRYPTO §3.3) | «Сопряжение не завершено, отсканируйте новый QR» | «Телефон не дождался подтверждения сопряжения» |
| `pc_offline` | `server` | ПК без связи дольше 5 минут (D-26) | «ПК был без связи дольше 5 минут» | «Не было связи с сервером дольше 5 минут» |
| — (`404`) | — | причина уже не хранится | «Сессии больше нет: её разорвала другая сторона» | то же |

`<N>` — срок простоя из QR словами («4 ч», «15 мин»). Незнакомая причина — «Сессия разорвана (<reason>)».

### 8.2. Что делает каждая сторона при разрыве

- Обе стирают ключи пары (CRYPTO §2) и всё состояние сессии: ПК — описания тредов, запросы, исходы; телефон — ленты,
  карточки, черновики, `feeds`.
- ПК отпускает ждущие хуки с «нет решения», без `resolved` телефону (ARCHITECTURE §5.4).
- Простой N отсчитывает только ПК от последнего события треда сессии; `wait_seconds` ограничен 540 с, а N — не меньше
  900 с, поэтому простой не наступает, пока ждёт хук: событие запроса само сдвинуло отсчёт (закрывает пункт этапа 3
  «срок ожидания хука больше N», D-90).

### 8.3. Вход на телефоне

Протокол во входе не участвует; порядок обязателен для mobile (D-88):

- Сессия на телефоне открывается только после входа: системный `BiometricPrompt` с
  `BIOMETRIC_STRONG | DEVICE_CREDENTIAL` (биометрия или PIN, пароль, графический ключ устройства).
- **До входа поток не открывается**, конверты не расшифровываются, ленты не показываются: для ПК телефон не на экране
  (D-60), окна текста не открываются.
- Вход повторяется при холодном старте и при возврате после блокировки экрана или сворачивания, если приложение было
  не на экране дольше **60 с** (порог D-51).
- Без защищённой блокировки экрана (`KeyguardManager.isDeviceSecure` — `false`) приложение не сопрягается и не
  открывает сессию: «Включите блокировку экрана — без неё Pult не защищён» (D-19, D-88).

## 9. Отрисовка недоверенной ленты

Всё содержимое `ct`, кроме перечислений, — недоверенный текст: в нём вывод инструментов, страницы из сети, файлы
проекта, слова собеседника-треда. Телефон обязан (D-89):

- Рисовать своими компонентами Compose. WebView, HTML-рендерер и загрузчики картинок для ленты не используются.
- **Не загружать ничего внешнего** — ни картинок, ни превью ссылок, ни шрифтов, ни файлов: лента не делает сетевых
  запросов.
- Разметку понимать только в полях, помеченных «разметка» (§3.3, §4.4), и только подмножество: абзацы и переводы
  строк, `*курсив*`/`_курсив_`, `**жирный**`, `` `код` ``, блоки кода в тройных обратных кавычках (моноширинно, без
  подсветки), заголовки `#`…`######` (жирной строкой), списки `-`/`*`/`1.`, цитаты `>`, ссылки `[текст](адрес)` (адрес
  без пробелов и скобок, перед `[` нет `!`) и голые адреса. Голый адрес — `http://` или `https://` и дальше символы до
  пробельного (§1.1), `<`, `>`, `"`, `'`, `` ` ``; с конца адреса снимаются все подряд идущие `.,;:!?)`. Остальное — таблицы, HTML-теги, сноски,
  картинки `![…](…)` — показывается исходным текстом, как написано; голый адрес внутри такого текста остаётся ссылкой. В
  коде ссылки не распознаются: код — `` `…` `` в одной строке и блок от ```` ``` ```` до следующего ```` ``` ````; блок без
  закрывающих кавычек кодом не считается. Вложенность списков и цитат — не глубже 4, глубже — плоско.
- **Ссылки сами не открываются.** Ссылка выглядит как ссылка, нажатие показывает диалог с полным адресом (не текстом
  ссылки) и кнопками «Копировать» и «Открыть»; «Открыть» есть только у `http` и `https`, остальные схемы (`intent:`,
  `file:`, `javascript:`, `content:`, `tel:`) — только копирование. Автоматического открытия, предзагрузки и
  распознавания адресов, телефонов и почты системой нет.
- Очистка — до разбора разметки, по порядку: `\r\n` и одиночный `\r` заменить на `\n`; остальные управляющие символы
  U+0000–U+001F и U+007F–U+009F, кроме `\n` и `\t`, — на `�` (U+FFFD); символы направления письма U+202A–U+202E,
  U+2066–U+2069, U+200E, U+200F удалить: ими подменяют видимый порядок текста и адреса.
- Поля «простой текст» и «моноширинно» показывать как есть, без разбора разметки; в названии треда и `peer_title` —
  одна строка, переводы строк заменяются пробелом.
- Вывод не исполняется и не копируется в буфер обмена без действия пользователя.

## 10. Что намеренно не передаётся

- Ход рассуждений модели, вложения и картинки транскрипта (вместо них — `unrecognized` или `notice` «вложение не
  показано»).
- Срок ожидания запроса и время до разрыва по простою: часы ПК и телефона не сверяются (CRYPTO §6).
- История тредов до сопряжения (D-30).

## 11. Эталонные примеры

[`vectors/messages.json`](vectors/messages.json) — открытые тексты (что лежит в `ct`), без шифрования:

| Раздел | Что | Кто обязан пройти |
|---|---|---|
| `valid` | по примеру каждого типа и каждого `kind`; получатель разбирает без ошибки, отправитель строит равный объект | desktop и mobile |
| `reject` | сообщения, которые получатель отбрасывает (`null`, тип поля, нет обязательного, `seq` не подряд, нарушенный предел) | получатель этого направления (`to`) |
| `choice_answers` | ответы на эталонный `choice_request`: `accept` и `reject` | desktop |
| `snapshot_cases` | состояние телефона до, снимок (части), состояние после — по шагам §6.4 | mobile |
| `feed_cases` | хранимые `seq`, входящие записи, ожидаемые пометки §6.5 | mobile |
| `tails` | `feeds` из `hello`, `last_seq` тредов — ожидаемые диапазоны хвостов §6.5 | desktop |
| `render` | входной текст, поле и ожидаемый результат правил §9 (ссылки, картинки, HTML, управляющие символы) | mobile |

`vectors/messages.py` (Python 3, только стандартная библиотека) проверяет файл эталонной моделью: без аргументов —
разбор `valid` и отказ на `reject`, ответы, применение снимков, пометки, хвосты и правила отрисовки; расхождение —
ненулевой код. Тест блока читает JSON из `protocol/vectors/`, значения в код не копирует.
